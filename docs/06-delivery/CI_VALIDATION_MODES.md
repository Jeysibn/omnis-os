# CI validation modes

The CI workflow uses two validation modes to reduce repeated work during Draft PR development while keeping the merge gate complete.

| Event                                               | Validation                                               | Required suites                                                                                                                                                                      |
| --------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Draft PR update                                     | Fast                                                     | Formatting, lint, typecheck, unit tests, web build, Compose configuration checks, host-security unit tests, and the shell browser smoke plus tests selected for changed UI files     |
| Sensitive Draft PR update                           | Fast plus matching suites                                | Fast checks plus disposable platform, Compose, database, or full-stack suites selected from changed paths                                                                            |
| Manual workflow dispatch                            | Fast by default; full when `full_validation` is selected | The selected mode runs on the chosen branch; a manual run does not replace the Ready PR merge-candidate run                                                                          |
| Ready for Review or Ready PR update                 | Full                                                     | Core checks, all frontend browser tests, full-stack browser integration, Compose/container verification, database upgrade and recovery, backup/restore, and platform security checks |
| Push to `main` or `security/post-audit-remediation` | Full                                                     | The same complete acceptance suite as a Ready PR                                                                                                                                     |

After this workflow is present on the default branch, Draft PR developers can request the expensive suites from **Actions → CI → Run workflow** by selecting the PR branch and setting `full_validation` to `true`. The input defaults to `false`. GitHub requires `workflow_dispatch` to be defined on the default branch, so this option is not available while this workflow change itself is still in Draft; its Ready event and changed-file suites remain available for validation.

The workflow always emits the stable `checks` and `frontend-browser` check contexts required by the active `main` ruleset. `frontend-browser` runs a narrow changed-area suite in fast mode and the complete browser suite in full mode. The `checks` aggregator reads results from the same workflow run. It rejects missing, skipped, cancelled, or failed jobs whenever the current mode or changed-file classification requires them. Fast validation deliberately leaves the required `checks` context unsuccessful, even when Stage A passes, because the active ruleset has no separate full-validation context. This prevents a Draft or manual fast run from appearing merge-ready while expensive suites were skipped. The Ready-for-Review run can satisfy `checks` only after the full jobs pass. Full jobs are skipped only for a Draft change that does not match their sensitive area; the Draft state itself is not a merge authorization.

The workflow runs on PR open, reopen, synchronization, ready-for-review, converted-to-draft, and edit events. Ready conversion, a new head commit, and base/edit updates trigger a new full-mode run. Strict required-check freshness and up-to-date branch enforcement remain configured in the repository ruleset.

`setup-node` continues to cache the pnpm package store. The workflow does not cache `node_modules`, browser executables, Docker build layers, secrets, or executable build artifacts. Draft changes to authorization, database, container, host-security, or workflow files run the corresponding early integration coverage instead of deferring all risk checks until review.

The fast mode validates application code and selected regressions. It does not establish production readiness, host-loopback ingress, WSL2 compatibility, host-managed service security, or real-provider authorization. PR #91's internal browser network remains a CI-only integration path; Docker host publication and the final deployment topology remain separate acceptance gates.
