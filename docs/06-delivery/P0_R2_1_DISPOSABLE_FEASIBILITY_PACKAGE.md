## Test authorization boundary

This file makes existing detailed test proposals easier to execute and review; it does not create an executable harness, policy, runnable gateway, CI workflow, listener, rootless Engine, or WSL2 environment. The owner explicitly authorized preparation and safe repository validation only. Guest-root account/cgroup/firewall/filesystem work, VM creation, WSL import/configuration, CI changes, and target-host activity require the separate decisions in the review packet. The current assignment does not authorize those actions.

Use the fixture specifications below as normative test inputs. Do not invent command lines against an unapproved or unimplemented service. A later approved test PR must bind each fixture to exact commands, binary/image hashes, identities, network, resource cap, external termination and cleanup code before execution. Use only dummy keys, synthetic IDs, canary files, synthetic DB rows, private dummy sinks and the pinned inert mock image. Never access CLI credentials, owner files, production databases, public endpoints or provider services.

### Allowed sequence after future approval

1. Review exact source SHA and close design-review findings.
2. Owner approves a named isolated Linux VM, no-uplink/private-only network, fixed compute/disk budget, permitted guest-root operations, evidence handling and independent kill/cleanup authority.
3. Run Groups 1–5 in the VM, in order. Any group stop condition blocks later groups. These tests do not prove WSL compatibility.
4. Only after VM results and independent review, owner may separately authorize a named imported WSL2 distro and Windows test profile. Run only the WSL-specific ingress/lifecycle cases; no current distro or global host settings.
5. Publish per-test records with exact tested SHA, fixture/image/policy hashes, platform versions, expected/actual observation, artifact hash, cleanup state and independent reviewer verdict.

## ADR-0012 ingress provenance matrix

The required invariant is that only an explicitly authorized Windows-local client reaches the owner-facing gateway; WSL-local, LAN, unrelated container and forwarded clients are denied. Every test uses separate positive and negative principals and records the path at the proposed enforcement boundary. A missing route or refused connection is not enough to prove a policy deny: collect the expected boundary counter/trace or mark the case inconclusive.

|---|---|---|---|

Correlate Windows-side request and WSL/container-side enforcement counter. | WSL-local loopback, WSL host address, direct container address and same/separate bridge peer with forged headers. If allowed/denied sources become indistinguishable at enforcement, reject the predicate. |

## Result rules and cleanup

- **PASS:** all stated positive controls succeed, every required negative case is observed at the named enforcement boundary, no forbidden effect occurs, resource/termination evidence is complete, and exact cleanup is confirmed by the independent termination authority.
- **FAIL:** a prohibited operation, packet, canary access, listener, replay, resource escape or control bypass is observed. Stop the relevant suite and mark the affected architecture requirement blocked.
- **BLOCKED:** required owner/security approval, prerequisite, isolation, enforcement mechanism, or cleanup authority is absent. No test is started.
- **INCONCLUSIVE:** a path did not reach the named enforcement point, telemetry/counters are missing, source identity was not measurable, positive and negative routes differ, the test is unsupported, or cleanup cannot be proven. Do not convert “no response” into a pass.

Before any future execution, a protected run manifest must include exact VM/distro ID, source SHA, fixture/image/config hashes, resource budget, allowed test IDs, termination authority, evidence paths/retention, created resource IDs and reviewer. Cleanup must use full IDs and approved labels from that manifest, verify exact membership and refuse ambiguous/unexpected resources. `docker compose down`, wildcard prune, shell traps, or manual deletion alone are not cleanup evidence. If the daemon is unavailable or a process survives, quarantine the environment and keep the run blocked pending owner/reviewer recovery decision.

## Vendor documentation reviewed

These references establish generic vendor-documented behavior only; they do not establish support of Omnis' proposed topology on the owner’s WSL2 build. Reviewed 2026-11-13.

- Docker [Rootless mode](https://docs.docker.com/engine/security/rootless/) and [UID/GID mapping](https://docs.docker.com/engine/security/rootless/uid-gid-mapping/): daemon and containers run in a user namespace; prerequisites include `newuidmap`/`newgidmap` and subordinate UID/GID ranges. This does not restrict the Engine API.
- Docker [Rootless tips](https://docs.docker.com/engine/security/rootless/tips/) and [troubleshooting](https://docs.docker.com/engine/security/rootless/troubleshoot/): cgroup flags require cgroup v2/systemd and delegated controllers or may be ignored; storage and network/port drivers have limitations. AppArmor and overlay network limitations are version/runtime specific and must be checked for the selected release.
- Docker [Port publishing](https://docs.docker.com/engine/network/port-publishing/): omitted host IP publishes on all host addresses; localhost binding is host-scoped, with a documented pre-28.0.0 same-L2 caveat; userland proxy and direct routing can alter reachability.
- Microsoft [WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking), [WSL configuration](https://learn.microsoft.com/en-us/windows/wsl/wsl-config), and [systemd in WSL](https://learn.microsoft.com/en-us/windows/wsl/systemd): NAT/mirrored modes, localhost forwarding, firewall and systemd are configurable/version-dependent; global WSL settings can affect multiple distros.
