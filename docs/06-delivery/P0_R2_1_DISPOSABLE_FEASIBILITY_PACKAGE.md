## Test authorization boundary

This file makes existing detailed test proposals easier to execute and review; it does not create an executable harness, policy, runnable gateway, CI workflow, listener, rootless Engine, or WSL2 environment. The owner explicitly authorized preparation and safe repository validation only. Guest-root account/cgroup/firewall/filesystem work, VM creation, WSL import/configuration, CI changes, and target-host activity require the separate decisions in the review packet. The current assignment does not authorize those actions.

Use the fixture specifications below as normative test inputs. Do not invent command lines against an unapproved or unimplemented service. A later approved test PR must bind each fixture to exact commands, binary/image hashes, identities, network, resource cap, external termination and cleanup code before execution. Use only dummy keys, synthetic IDs, canary files, synthetic DB rows, private dummy sinks and the pinned inert mock image. Never access CLI credentials, owner files, production databases, public endpoints or provider services.

## Ordered test stages and dependencies

2. **B — Minimal disposable Linux VM tests (owner authorization required):** P0 inventory; E1–E4 rootless daemon prerequisites/effective config, identities, sockets, storage and aggregate cgroup controls; N1-B/N2-B synthetic-process and synthetic local-IPC checks; listener-detector positive control. ### Evidence sanitization contract

For every process boundary, capture an allowlisted inventory only: environment variable **names and present/absent/type**, never values; mount **category, read/write flag and synthetic fixture ID**, not arbitrary host paths or contents; file descriptors as **number, type and sanitized class** (socket/pipe/file/memfd), never contents or secret paths; service UID/GID, maps, cgroup path/limits, systemd unit and config/artifact digests. Use synthetic canaries and credentials created inside the disposable VM. Do not read existing CLI credential directories, home files, provider stores, raw process environments or secret contents. If a tool cannot produce a sanitized inventory without exposing values, stop and mark that fixture BLOCKED.

## Stage B/C prerequisite correction

Stage B is intentionally limited to a real rootless daemon and controls that can be directly exercised without the future Gateway, Authorizer reservation ledger, Gateway journal or per-run terminator. Its E1–E4 rows cover daemon facts, identity/storage and whole-service aggregate limits; they do not claim API confinement or per-run termination. E5 (gateway-mediated Engine configuration), E6 (the actual protected Engine socket/FD boundary), G-series, concurrent journal, active-workload recovery and Engine/RootlessKit N1/N2 are Stage C only. Stage B N1-B/N2-B use a synthetic host process bound to the selected external enforcement point and private sink, and prove only that enforcement point. Missing a needed implementation is BLOCKED, never a reason to skip a prerequisite or report PASS.

## Result rules and cleanup

- **PASS:** all stated positive controls succeed, every required negative case is observed at the named enforcement boundary, no forbidden effect occurs, resource/termination evidence is complete, and exact cleanup is confirmed by the independent termination authority.
- **FAIL:** a prohibited operation, packet, canary access, listener, replay, resource escape or control bypass is observed. Stop the relevant suite and mark the affected architecture requirement blocked.
- **BLOCKED:** required owner/security approval, prerequisite, isolation, enforcement mechanism, or cleanup authority is absent. No test is started.
- **INCONCLUSIVE:** a path did not reach the named enforcement point, telemetry/counters are missing, source identity was not measurable, positive and negative routes differ, the test is unsupported, or cleanup cannot be proven. Do not convert “no response” into a pass.

Before any future execution, a protected run manifest must include exact VM/distro ID, source SHA, fixture/image/config hashes, resource budget, allowed test IDs, termination authority, evidence paths/retention, created resource IDs and reviewer. Cleanup must use full IDs and approved labels from that manifest, verify exact membership and refuse ambiguous/unexpected resources. `docker compose down`, wildcard prune, shell traps, or manual deletion alone are not cleanup evidence. If the daemon is unavailable or a process survives, quarantine the environment and keep the run blocked pending owner/reviewer recovery decision.

## Vendor documentation reviewed

These references establish generic vendor-documented behavior only; they do not establish support of Omnis' proposed topology on the owner’s WSL2 build. Reviewed 2026-11-13.

- Docker [Rootless mode](https://docs.docker.com/engine/security/rootless/) and [UID/GID mapping](https://docs.docker.com/engine/security/rootless/uid-gid-mapping/): daemon and containers run in a user namespace; prerequisites include `newuidmap`/`newgidmap` and subordinate UID/GID ranges. This does not restrict the Engine API.
- Docker [Rootless tips](https://docs.docker.com/engine/security/rootless/tips/) and [troubleshooting](https://docs.docker.com/engine/security/rootless/troubleshoot/): cgroup flags require cgroup v2/systemd and delegated controllers or may be ignored; storage and network/port drivers have limitations. AppArmor and overlay network limitations are version/runtime specific and must be checked for the selected release.
- systemd [resource control](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html): `IPAddressAllow=`/`IPAddressDeny=` use cgroup-based controls where supported; effective version, cgroup attachment and descendant behavior remain experimental requirements, not a verified control here.
- nftables [packet metadata matching](https://wiki.nftables.org/wiki-nftables/index.php/Matching_packet_metainformation): `meta skuid` is a candidate match for the local socket UID. RootlessKit helper ownership and packet attribution must be experimentally established before relying on it.
- Docker [Port publishing](https://docs.docker.com/engine/network/port-publishing/): omitted host IP publishes on all host addresses; localhost binding is host-scoped, with a documented pre-28.0.0 same-L2 caveat; userland proxy and direct routing can alter reachability.
- Microsoft [WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking), [WSL configuration](https://learn.microsoft.com/en-us/windows/wsl/wsl-config), and [systemd in WSL](https://learn.microsoft.com/en-us/windows/wsl/systemd): NAT/mirrored modes, localhost forwarding, firewall and systemd are configurable/version-dependent; global WSL settings can affect multiple distros.

For Docker-only WSL2, Docker manages the Core and synthetic runtime workloads through separate rootless Engines; the proposed Authorizer, Worker, Gateway, registrar and termination controls are host infrastructure, not Compose services. Anchor failure leaves the proposed durable request fence in place and must be shown to the owner as pending, not yet protected. Restore that omits or conflicts with a pending request is quarantined. Start issuance additionally requires durable trusted stop-registration acknowledgement. The controlling packet specifies the narrow privileged actuator API and stop-lease validity through deadline/grace/evidence, plus clock uncertainty behavior and negative fixtures. The [N-2/N-3 cancellation and anchor ordering contract](./P0_R2_1_SECURITY_REVIEW_PACKET.md#n-2n-3-authoritative-cancellation-and-db-to-anchor-ordering) controls the related lifecycle, state and test tables. After an independent irreversible anchor pre-fence, Authorizer commits tombstone/revision/outbox atomically; committed revocation/supersession immediately denies new reservations. Only a persisted matching independent anchor receipt establishes durable rollback protection. Pending/uncertain anchor or restored state fences new execution; held independent stop leases remain effective. Cancellation requires terminator/actuator evidence for the exact run/generation; Gateway/daemon observations are advisory.

N-3 ordering requires an independent irreversible intent pre-fence **before** authoritative DB revocation/supersession commit, then final anchor receipt after commit. Every issuance/consumption obtains fresh anchor admission bound to exact revisions; unresolved pre-fences deny restored old authority. A durable local request fence is persisted before anchor contact; anchor/pre-fence uncertainty leaves execution denied and owner-visible as pending, not yet protected. Held stop leases still enforce deadlines. A successful pre-fence is never removed because DB commit failed; recover the original transition. These proposed Option A semantics remain unimplemented and M-3 remains owner-gated. The controlling packet also resolves N-5 (no selected API channel or implicit host UID mapping) and N-7 (pre-fence-first denies an unconsumed reservation; consume-first allows only that step once).

External pre-fence states `PREFENCED_DB_PENDING` / `LEASE_PREFENCED_DB_PENDING` precede DB commit and deny new ticket issuance and consumption of any ticket still `RESERVED`. If a matching `CONSUMED` receipt is ordered before the pre-fence, only that exact step may proceed once; uncertain dispatch remains UNKNOWN and cannot replay. Recovery commits the same transition after DB failure/lost result or remains fenced; these are distinct from post-DB anchor-finalization pending and never revert to ACTIVE.
