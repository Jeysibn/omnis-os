# Normative secure release, authorization, IPC, and validation contract

## Authorities and owner authorization

A dedicated host-side **Authorization Issuer** owns authorization issuance. It is separate from the web/API process, fixture, Stage 1 admission controller, and Stage 2 release authority. It verifies owner authentication through the existing owner-authentication mechanism only after its session-verification interface is specified and reviewed. It must query a live session authority on every issue and immediately before consumption; session ID possession or caller-supplied claims are insufficient. Current interface does not exist. Until owner selects and reviews its trust anchor, authorization issuance is unavailable and release is denied.

Each immutable authorization record includes random authorization ID, issuer key ID/signature, owner subject ID, active session ID and session generation, operation ID, run ID, Stage 1 generation and session, manifest digest, attempt ID/path/ordinal/request digest, fixture role and immutable fixture generation/config/image digest, boot ID, issue and expiry BOOTTIME, exact deadline no later than the original Stage 1 deadline, single-use flag, and revocation sequence. No wildcard fixture, operation, generation or deadline. Issuer persists issue record before returning it.

Issuer signing key is root-owned, non-exportable where available, and readable only by issuer; private signing key never enters API/container. Release authority pins issuer public key and issuer identity. Key custody is an owner decision and implementation dependency. Authorization ID is lookup only, never proof of owner identity. Authorization is single-use. Expiry, boot mismatch, wrong owner/session/operation/fixture/generation, invalid signature, stale revocation sequence, revoked or already consumed record denies.

Session invalidation is an issuer-signed monotonic revocation event. Revocation and consumption serialize through the same release-ledger lock and ordered sequence. If revocation commits first, consumption fails. If consumption commits first, authorization is consumed; revocation cannot undo an already committed release, but it closes any remaining gate and requests termination. The issuer must publish revocation durably before acknowledging logout/invalidation as effective. During issuer/session-authority unavailability, new authorizations and unconsumed releases fail closed; already consumed release is handled by supervisor, never retried. Concurrent operations are linearized by ledger commit sequence, not wall-clock claims.

## Request, validation, and consumption ordering

Only the live original Stage 1 controller session requests release. Only the Stage 2 authority authorizes/consumes. Only the intended inert bootstrap can pass the final execution fence. API, browser, shell, and Docker client do not issue release commands.

Request contains exact authorization identity plus Stage 1 snapshot fields, immutable fixture identity/generation, bootstrap nonce, cgroup identity, boot ID, observer readiness generations, supervisor invocation, and canonical digest. Strict schema, bounded size, no unknown keys; no command, path, image, timeout or destination chosen by caller.

1. Authenticate controller peer and request; lock Stage 2 ledger.
2. Verify issuer signature and live owner/session status using the approved issuer interface; check operation and exact fixture scope; reject expiry, boot or revocation mismatch.
3. Call Stage 1 `validateReservation` (read-only, under Stage 1's own lock/storage boundary). Verify original controller session, journal state, reservation, digest, run generation and Stage 1 deadline. Return to Stage 2 and recheck issuer revocation sequence while holding release serialization.
4. Verify fixture/bootstrap/config/cgroup/observer identities and armed supervisor. Persist `release_authorized` intent.
5. Atomically consume authorization in the durable Stage 2 ledger, fsync file, rename, fsync directory; recheck boot/deadline and revocation sequence. Only this commit spends permission. Any ambiguous commit poisons the run; no send/retry.
6. Send one bounded authenticated permit to the pinned inert bootstrap. A send result/ack is not proof of execution. Duplicate request yields non-actionable status only.

## Normative deadline-to-execution rule (V3)

The original Stage 1 deadline is an absolute boot-bound `CLOCK_BOOTTIME` value and is never extended or reset. **No application execution may begin at or after that deadline.** Application execution begins at the first instruction executed from the fixture's application-controlled entrypoint. Trusted inert bootstrap instructions used only to validate and await a permit are not application execution; they must remain incapable of loading plugins, opening the fixture listener, making requests, or invoking the application entrypoint.

A Stage 2 ledger commit or authorization gate opening is not evidence that application execution began. The required authorization linearization point is a kernel-enforced event that atomically (a) samples the same boot's monotonic clock, (b) verifies the exact one-use permit and unexpired deadline, and (c) admits the first application instruction. The comparison is strict: `now < deadline` permits; `now >= deadline` denies. The event must be ordered against supervisor freeze/kill so exactly one wins: if expiry/freeze wins, no application instruction runs; if the application-entry event wins, kernel evidence proves it occurred before expiry. A userspace timestamp followed by `exec`, thaw, scheduling, or acknowledgement cannot establish this ordering.

The trusted enforcement component must emit durable evidence binding boot ID, exact cgroup/process identity, permit digest, Stage 2 consumed-ledger sequence, kernel-clock sample, and the kernel linearization event. Evidence of gate opening, successful `execve`, or container start alone is insufficient because the task may be descheduled before its first application instruction. Any scheduling delay before the linearization event is naturally denied once the deadline passes. After a successful linearization event, scheduling delay does not change the fact that execution began before expiry, but supervisor must still terminate within the existing absolute cleanup bounds.

Candidate mechanisms for research only: a reviewed kernel extension/LSM hook at the application-entry boundary with a deadline-aware admission primitive; a runtime/kernel facility with equivalent atomic first-instruction admission; or redesigning the fixture so the only application instruction is a kernel-mediated, deadline-checked transition. `ptrace` stop/continue, userspace timers, systemd timers, cgroup freeze/thaw, Docker API start, signed expiry claims and a pre-exec clock check do not by themselves close the scheduling race. No candidate is selected or established on the target WSL2 kernel. Docker/WSL2 currently has no demonstrated mechanism proving this required first-instruction ordering. Therefore **RELEASE BLOCKED — DEADLINE FENCE NOT ESTABLISHED** until security review and target-host evidence prove one.

The bootstrap remains inert and held in the pre-created frozen cgroup. A single consumed permit is delivered once. Bootstrap must ask the trusted fence component for the atomic entry event; late delivery, descheduling, expired clock, identity mismatch, missing fence, or supervisor freeze yields denial and no application entry. Delayed Docker start must join the exact frozen cgroup before any fixture instruction; if runtime cannot prove this, no container is created/released. The supervisor arms freeze/termination before any permit can be consumed, and its finalizer races through the same kernel-enforced fence. If fence ordering or enforcement is unavailable, remain blocked; do not claim gate opening means execution began.

## Stage 1 liveness and consumption ordering (V3)

V2's read-only `validateReservation` snapshot releases Stage 1's stable lock before Stage 2 consumption. A controller can terminate after its live-session snapshot and before the Stage 2 durable commit. PID, starttime, pidfd polling, a held Stage 1 lock in another process, or an earlier liveness sample cannot atomically prove “controller alive at Stage 2 commit.” Therefore the V2 protocol does not satisfy its stated rule that controller death before consumption denies release.

No reliable cross-process atomicity protocol is established. Holding Stage 1's stable lock while Stage 2 commits avoids concurrent journal mutation but does not prevent controller death and creates a cross-store failure window; lock ownership does not prove process liveness. Lock order must never become Stage 1→Stage 2 while Stage 2→Stage 1 exists. A pidfd/liveness check immediately before commit still races with death between check and durable ledger commit. Controller restart remains terminal under Stage 1; it cannot adopt the prior session.

**Required status: LIVE STAGE 1 INTEGRATION BLOCKED — LIVENESS ORDERING UNPROVEN.** No live adapter may be enabled. Stage 2A may use a fake validation adapter only.

Alternative B for a separately reviewed contract amendment: redefine the Stage 1 result as an immutable, durable validation lease whose validity is linearized by Stage 1's own committed record, and explicitly state that controller death after that Stage 1 linearization does not revoke the result. Stage 2 may consume only that lease before original deadline, under a signed sequence and one-use binding. This changes the semantics from “controller death before Stage 2 consumption denies” to “controller death after Stage 1 lease commit does not retroactively invalidate the lease.” It needs a Stage 1 contract extension, owner approval, Codex #1 review, and independent security review. It does not by itself solve deadline-to-first-instruction. Until amendment approval, no live Stage 1 integration or release-capable implementation is authorized.

## IPC trust anchors

Candidate is root-owned AF_UNIX SOCK_SEQPACKET in a dedicated host-controlled directory, but it is disabled until this identity matrix passes. Distinct dedicated UIDs/GIDs: issuer, Stage 1 controller, release authority, supervisor/helper, fixture bootstrap; no shared UID with API or untrusted workloads. Socket parent root:root 0710 with only named group traversal; socket owned authority UID and dedicated controller group, mode 0660; no writable parent for clients. Listener pins opened directory/socket device+inode, rejects symlink/hardlink replacement, revalidates after bind, and never follows a replaced path. No bind-mounted socket into general containers; fixture channel is a separately created per-fixture socket with exact mount and generation.

Mutual authentication requires kernel `SO_PEERCRED`/`SCM_CREDENTIALS` plus trusted host-side mapping from peer PID namespace to host PID, PID starttime, UID/GID, cgroup, systemd unit invocation ID, and executable file identity (device/inode plus immutable package digest verified by root-owned launcher). Server client checks peer; client verifies server through pinned socket inode and server PID/unit/executable identity obtained from trusted host supervisor. UID/PID/path alone are insufficient. PID reuse is rejected with starttime and boot binding. Same-UID impersonation is prevented by dedicated UID isolation and inaccessible credentials; if a process can run as the same UID, channel is compromised and disabled. No SCM_RIGHTS, inherited unexpected FDs, `/proc/<pid>/fd` authority, or arbitrary descriptor receive; peer messages contain no descriptors. Cross-container credentials are interpreted in host namespace only through trusted runtime mapping, never container-reported PID/UID. If credential translation or executable/unit evidence is unavailable/inconsistent, no fallback to socket permissions: release stays disabled.

Trust anchors: root-owned system manager and pinned immutable helper package; kernel peer credentials and procfs mapping; issuer public key. These are assumptions, not target-proven facts. Root/host/kernel compromise is outside threat model. Each UID, mapping, unit and socket rule requires owner approval. No Stage 1 implementation change is included; the validation interface extension requires separate review.

## Failure semantics

Expired/wrong owner/session/fixture/operation, replay, stale revocation sequence, issuer outage, session invalidation, Stage 1 terminal/poisoned state, stale reservation, peer mismatch, missing identity or ambiguous commit/send all deny new release. Revocation-before-consume denies; consume-before-revocation remains consumed and triggers termination if revocation arrives. Controller death before consume: deny. After consume: never retransmit; supervisor terminates/reconciles. Lost ack: status query only. Restart, boot change, deadline expiry or unknown state: recovery required, admission closed. No exactly-once physical execution claim; ledger proves authorization consumption only.
