## Controlling architecture correction (2026-11-13)

This section supersedes the earlier “Candidate topology under review” and every statement below that allows the Gateway to be a container managed by the Runtime Engine or provisioned/updated by the Runtime Engine operator. That packaging alternative is withdrawn and is not a valid target. The only candidate for review is: Core web/API/PostgreSQL in the Core rootless Engine; Worker, Launcher, Authorizer and Runtime API Policy Gateway as separate host systemd services under distinct non-login host UIDs; Runtime Engine as a separate rootless host service under its own UID and subordinate-ID range. Host UID peer checks apply only to these host services. Container UIDs are namespaced and must never be treated as equivalent; actual map and impersonation tests are mandatory. The complete socket, ownership, Worker identity, authorization race, payload and journal contract is in [the current security review packet](./P0_R2_1_SECURITY_REVIEW_PACKET.md), which controls where this historical design text conflicts. ## Executive assessment

The dual-rootless-Engine architecture remains a candidate, not an approved runtime. A compromised launcher cannot safely hold an unrestricted Runtime Engine socket: Docker documents an all-or-nothing default API authorization model. A Docker authorization plugin is a credible defense-in-depth control but is **not sufficient by itself**: Docker's documentation says native and HTTP-upgraded gRPC calls bypass authorization plugins, non-JSON request bodies are not exposed to the plugin, and hijacked/streaming operations receive limited inspection.

The credible candidate is a **separate Runtime API Policy Gateway** that alone holds the Runtime Engine socket. The launcher receives only a private, versioned policy endpoint (preferably UDS); the gateway validates a bounded run capability and sends a reconstructed request to the daemon. The raw Engine socket is absent from the launcher, Core Engine containers, and synthetic runtime. An authorization plugin may add defense-in-depth only after rootless compatibility is demonstrated. Gateway code/configuration must be outside launcher control and fail closed. A separate host/network boundary must deny all Runtime Engine egress even if a malicious request or policy bug creates another network.

The only candidate IPC path is a host-to-host AF_UNIX socket between the host Launcher and independently provisioned host Gateway; exact host `SO_PEERCRED` is required. There is no shared IPC volume, and both peers are outside user namespaces. If implementation requires exposing the raw Runtime Engine socket to Core or Launcher, stop and report **P0-R2.1 BLOCKED — NO INDEPENDENT API OR EGRESS ENFORCEMENT**.

## Threat model and architecture candidate

### Adversary and protected assets

Assume the Launcher service process is fully compromised: the attacker can read every file and environment value available to that service and can send arbitrary requests to every endpoint it can reach. Do not rely on launcher-side request validation, Docker flags supplied by it, Compose network membership, a caller-supplied `workerId`, or secrecy of a token readable in the launcher.

Protect: Core Engine and its socket/data; API, authorizer, PostgreSQL, their secrets and volumes; owner/Windows files; host kernel and WSL configuration; external network and LAN; image provenance; run authorization/generation; and resource availability. Only synthetic output and a bounded per-run workspace may cross into the runtime sandbox. No real provider key, fixture, owner data, or production database is present in the harness.

### Candidate topology under review

The first-class stop component is `omnis-runtime-terminator`, a distinct non-login host systemd service with root-owned unit/binary and its own root-parented stop UDS. It accepts only Authorizer-authenticated stop-only capabilities; it has no Runtime Engine socket and no policy/update authority. Gateway and terminator are separate units and cgroups. The trusted per-run cgroup registration mechanism is **OPEN — DESIGN**; no per-run termination guarantee or PASS is claimed. Whole Runtime service termination is a coarse owner-approved fallback only, and VM destruction remains final cleanup. See the security review packet for exact stop claims, key custody, cgroup evidence and owner gates. The reviewed `5578b1b` revision received conditional verdicts from both reviewers; their focused re-review of this delta remains pending.

```text
Core rootless Engine: web/API/PostgreSQL and Core-only volumes
Host services: Worker ↔ Launcher ↔ Runtime API Policy Gateway
              Worker/ Gateway ↔ Authorizer (separate authenticated UDS paths)
Runtime rootless Engine: synthetic runtime containers only
Host provisioner/system manager: owns all service executables, units and policy;
  sole authority to provision/update/restart Gateway; never controlled by either Engine
```

This is a candidate diagram, not implementation. The raw Runtime Engine socket is not shared with the Core Engine and is not mounted into the launcher or any container. The Gateway is an independently managed host system service and cannot be provisioned, replaced, updated, or restarted through either Engine. Host UDS peers are authenticated by exact host `SO_PEERCRED` UID/GID and protected socket paths; no container peer mapping is assumed. The two rootless daemons remain separate authorities. The Runtime Engine daemon is trusted and its compromise is outside the Gateway's protection; owner acceptance or a stronger VM boundary is required. Gateway compromise is a stop condition, not an accepted residual.

No Docker client credential, rootless account credential or Engine socket crosses between Engines. Any per-run authorization material crossing the policy UDS must be a Codex #1-approved, operation-scoped capability that confers no generic Docker API authority; it is application authorization data, not an Engine credential.

The runtime account must have no access to Core Engine data, app secrets, `/home/<owner>`, `/mnt/c`, Windows credentials, or arbitrary host paths. Runtime Engine images and policy are provisioned by a separately controlled setup path, then the rootless daemon's own exposed API cannot change policy or install/update the gateway. The exact provisioning/control boundary remains for Codex #1 and owner approval.

### Resource envelope and storage controls

All figures are planning budgets, not measured requirements. Hypervisor limits cap total guest CPU, memory and disk. Within the guest, systemd/cgroup-v2 parent slices cap the complete Runtime Engine process tree and all delegated child cgroups; the launcher cannot raise parent `CPUQuota`, `MemoryMax`, or `TasksMax`. If rootless Engine cannot enforce cgroup-v2 limits as configured, the test fails closed; never silently accept ignored Docker limits.

Use a dedicated fixed-size Runtime Engine data filesystem with hard block and inode quotas. Keep images/layers, named runtime volumes, scratch, temporary files, and rotated logs within this one quota boundary. Do not rely on per-container `storage-opt` or user-controlled volume settings as the aggregate limit. A rootless request cannot enlarge the backing virtual disk or filesystem quota. API policy caps active containers, per-run scratch size, output bytes, log bytes, and retained stale resources. Runtime image is imported by digest before egress is blocked; the exposed API cannot pull/build/load/tag images or alter daemon config. Disk-full, inode-full, memory-pressure, PID exhaustion, and log-quota scenarios must return resource-exhausted/unknown states, retain authorization history, deny new starts, and never auto-replay. Evidence includes cgroup tree/effective controller values, filesystem quota/inode use, image/volume/log inventory and daemon status before/after.

**Superseded and withdrawn:** the prior text said the Runtime Engine operator provisions a pinned Gateway container. That is not a valid architecture. The Runtime Engine socket is a host UDS available only to the Gateway service UID. No `containerd.sock`, runtime-shim socket, alternate Docker context, TCP daemon endpoint or credential file is exposed to Worker, Launcher, Core services or workloads.

## Independent egress-denial design

The primary boundary is outside launcher control: run the **Runtime Engine daemon and its rootless network helper inside a dedicated network namespace with no external interface/default route**, with IPv4 and IPv6 default-deny output at the namespace/VM boundary. The only launcher-to-gateway IPC is a Unix socket, so no listener is needed on a bridge or host port. Do not attach the Runtime Engine to the Core Engine network. Do not rely on `network=none` passed by the launcher or gateway alone.

If WSL cannot provide a stable no-uplink namespace boundary, the VM harness may additionally apply guest-root-owned nftables/Windows Hyper-V egress deny for the isolated test VM. Runtime traffic must remain denied even if the gateway creates an alternate network or publishes a port. These controls are test candidates, not approved changes to the owner's WSL or firewall. If a rootless container can reach an external route despite the outer boundary, stop: the architecture is blocked until a separate enforceable denial exists.

## Local HTTPS ingress proof plan

Retain exact local origin `https://localhost:8443`; **LAN exposure is not an option**. The eventual gateway publishes only WSL loopback `127.0.0.1:8443` (and `::1` only if deliberately configured and verified); no wildcard bind, public address, portproxy, tunnel or LAN rule. API, worker, PostgreSQL, authorizer, launcher and Runtime Engine have no host-published application ports.

Acceptance is staged: in the disposable WSL test distro, use a synthetic local CA/leaf cert trusted only in the disposable Windows test profile. Verify Windows browser positive access to exact localhost origin; valid certificate chain/SAN; session cookie `Secure; HttpOnly; SameSite=Strict`; exact Host and Origin; session-bound CSRF; same-origin mutation succeeds; foreign Origin, absent token, malformed Host and forwarded-header spoof fail. Verify SSE uses same-origin cookie, preserves `Last-Event-ID`, reconnect reauthenticates and does not buffer. Inspect Docker effective published ports and Windows/WSL listener tables for IPv4 and IPv6. Microsoft documents that mirrored WSL networking does not support Windows-to-WSL `::1` localhost forwarding; do not infer it works. The [N-2/N-3 cancellation and anchor ordering contract](./P0_R2_1_SECURITY_REVIEW_PACKET.md#n-2n-3-authoritative-cancellation-and-db-to-anchor-ordering) controls the related lifecycle, state and test tables. After an independent irreversible anchor pre-fence, Authorizer commits tombstone/revision/outbox atomically; committed revocation/supersession immediately denies new reservations. Only a persisted matching independent anchor receipt establishes durable rollback protection. Pending/uncertain anchor or restored state fences new execution; held independent stop leases remain effective. N-3 ordering requires an independent irreversible intent pre-fence **before** authoritative DB revocation/supersession commit, then final anchor receipt after commit. Every issuance/consumption obtains fresh anchor admission bound to exact revisions; unresolved pre-fences deny restored old authority. Anchor/pre-fence uncertainty defers authoritative commit and denies new execution; held stop leases still enforce deadlines. A successful pre-fence is never removed because DB commit failed; recover the original transition. These proposed Option A semantics remain unimplemented and M-3 remains owner-gated.

External pre-fence states `PREFENCED_DB_PENDING` / `LEASE_PREFENCED_DB_PENDING` precede DB commit and deny new ticket issuance and consumption of any ticket still `RESERVED`. If a matching `CONSUMED` receipt is ordered before the pre-fence, only that exact step may proceed once; uncertain dispatch remains UNKNOWN and cannot replay. Recovery commits the same transition after DB failure/lost result or remains fenced; these are distinct from post-DB anchor-finalization pending and never revert to ACTIVE.
