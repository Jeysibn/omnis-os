## P0-R2 decision

The owner has set Docker-only as the final application topology, rejected any launcher container with access to the **rootful** Docker socket, and classified the current host-managed launcher as transitional only. The current candidate uses Docker Engines for Core and synthetic workload containers, with separate host control services for Worker, Authorizer, Launcher, Gateway, registrar and termination. If Docker-only means every service must run inside Docker, this candidate does not satisfy the owner target and must be rejected. A temporary rootful-socket hybrid exception requires separate owner authorization and is not Docker-only readiness.

The current code still implements a hybrid topology. This revision does not approve a replacement daemon or launcher. The strongest candidate to investigate is **two separate rootless Docker Engines**, each under a dedicated least-privilege WSL Linux service account: the Core Engine owns web/API/PostgreSQL containers; the Runtime Engine owns synthetic workload containers only. Worker, Authorizer, Launcher and Runtime API Policy Gateway remain proposed host systemd services under separate identities. This means Docker manages application/workload containers, while host control services remain explicit WSL infrastructure; reject the candidate if Docker-only excludes those host services. The Gateway alone holds the **Runtime Engine's** rootless socket; Launcher receives only the Gateway's private policy UDS. API and Worker receive neither Engine socket. A rootless socket holder has full administrative authority over every resource in that Engine; it is not method-restricted. The Gateway must therefore enforce a narrow API outside Launcher control, and separate Engine accounts/data roots must prevent Launcher compromise from controlling PostgreSQL, Authorizer, API, or control-plane secrets. Runtime Engine egress must be denied outside Launcher/Gateway options. This is only a design candidate: exact WSL2 user-namespace, UID/GID, cgroup, storage, networking, cross-Engine policy UDS, Gateway enforcement, filesystem, and lifecycle behavior is unverified.

Docker's documented rootless-in-Docker recipe requires an outer `--privileged` container. That recipe is **rejected** for this design. A non-privileged nested rootless daemon is an open feasibility question and must not be assumed to work. If the split-rootless candidate cannot meet the proof matrix, mark Docker-only blocked; do not fall back to a rootful socket container or silently retain the host launcher.

P0-R2.1 requires exact-head Codex security and cross-document reviews before any harness implementation or execution. No implementation, host experiment, CI trigger, or operational acceptance is authorized.

## Rootless daemon feasibility and authority

Docker Engine's official rootless documentation describes a per-user daemon, a socket normally at `/run/user/<uid>/docker.sock`, `newuidmap`/`newgidmap`, and at least 65,536 subordinate UIDs/GIDs. Rootless mode removes root privilege from dockerd; it does **not** make its socket harmless or narrow its API. A process that can use that socket controls all containers, networks, images, volumes and daemon-readable paths for that daemon account. Therefore the design separates a Core Engine account from a synthetic-runtime Engine account, each with disjoint subordinate IDs, private data roots and no owner/Windows files or unrelated secrets. Only the Runtime API Policy Gateway receives the Runtime Engine socket; Launcher, API, Worker, web, Authorizer and synthetic runtime see neither raw socket. Worker, Authorizer, Launcher and Gateway are separate host control services, not Core Compose services. The Gateway still has full Runtime Engine authority, so it must enforce a separate policy, not merely relay Launcher arguments.

Rootless resource enforcement is conditional: Docker documents cgroup limits only with cgroup v2 and systemd; without supported delegation the daemon can ignore container CPU/memory/PID limits. Storage driver support is kernel- and filesystem-dependent (`overlay2` requires kernel 5.11+, or `fuse-overlayfs`/other documented options). Rootless networking uses a user-mode network boundary with feature differences; Docker documents that overlay networks are unsupported. These generic Linux docs do not prove the owner's WSL kernel, AppArmor/userns policy, cgroup delegation, storage, port publishing or Compose behavior.

Microsoft documents WSL systemd support on sufficiently recent WSL, per-distro cgroup-v2 configuration and WSL NAT/mirrored networking controls. It also documents that systemd services do not keep a WSL instance alive after its normal lifecycle would stop. Docker's rootless systemd user service/linger instructions therefore do not alone establish service availability or restart after WSL shutdown. Exact WSL version, distro, kernel, systemd, cgroup controllers, subuid/subgid, rootless networking, `/mnt/c` access, and lifecycle must be captured in an authorized target acceptance run. None was probed here.

### Candidate rootless design requirements

The recommended feasibility candidate is a **split rootless design**: one Core Engine account owns web/API/PostgreSQL Compose services; a second Runtime Engine account owns synthetic execution. Worker, Authorizer, Launcher and Runtime API Policy Gateway are separate host systemd services. Only the Gateway receives the Runtime Engine's raw UDS. Launcher calls a private policy UDS, never the Docker Engine API. The Gateway enforces a narrow endpoint/body allowlist, capability and operation state, and reconstructs requests; it rejects gRPC, upgrades, unknown content types and every unknown route. A Docker AuthZ plugin may provide defense-in-depth only; official docs disclose gRPC and streaming gaps, and rootless support is unverified. An outer no-uplink network namespace/firewall independently denies egress. If the Gateway cannot prevent all raw-socket bypasses or the no-egress boundary cannot be proven, Docker-only is blocked.

The candidate is not implementation-ready until it proves all of the following:

- **User and file boundary:** dedicated OS account, non-overlapping subuid/subgid map, private daemon home/data/runtime directory, no read access to owner's home, repository, `/mnt/c`, Windows interop credentials, backup keys, or unrelated services. Use an owner-approved systemd/user namespace policy or WSL mount policy and prove denial by running as the actual daemon UID. A container path allowlist is insufficient if the daemon account can read arbitrary host paths.
- **Socket identity and daemon separation:** prove separate core/runtime daemon UIDs, subordinate maps, sockets, data roots, and volumes. Runtime socket owner/mode and mapping must allow only the policy gateway; prove launcher, API, worker, web, authorizer and synthetic runtime cannot access either raw Engine socket. Prove launcher can reach only the policy UDS and cannot bypass it through another mount/network path. A bind mount marked read-only does not make a Unix socket's protocol read-only.
- **Workspace and volumes:** daemon-side path resolution, ownership mapping, symlink/race protections, scratch cleanup, Postgres named-volume ownership, and persistence under WSL restart. No `/mnt/c`, `/home/<owner>`, Docker config, or arbitrary host path binds.
- **Synthetic operation:** existing Docker client operations and fixed digest image work unchanged or with reviewed adaptation; a daemon-side policy mechanism independently enforces image digest, command, no credentials/host paths, `network=none`, read-only root, dropped caps, no-new-privileges, non-root runtime, bounded workspace/output and no runtime socket. Prove that the selected mechanism is supported by rootless Engine, cannot be changed through the runtime API, and denies hostile daemon API requests from a compromised launcher. Deny egress independently of launcher flags. If no such enforceable mechanism is supported, stop: no current candidate meets the mock-only boundary.
- **Resource limits:** CPU, memory, PID, file descriptor, disk/output and wall-time ceilings are effective. Fail closed if rootless daemon silently ignores any required limit. Verify cgroup v2 + systemd and delegated controllers before using those flags.
- **Lifecycle:** Compose startup ordering, daemon socket readiness, launcher restart, rootless daemon restart, WSL termination/restart, cancellation, and DB recovery. On any uncertain create/start result, persist an `unknown`/recovery-required state, inspect by immutable run label/ID, and never automatically replay a launch.
- **WSL ingress/network:** rootless Docker's port forwarding, loopback-only bind, source-address behavior, private Compose networks and synthetic `--network=none` are checked under the owner's actual WSL mode and firewall. Source IP is not an authentication factor.

The official rootless-in-Docker example (`docker:<version>-dind-rootless`) uses an outer `--privileged` container to disable seccomp, AppArmor and mount masks. That exact pattern expands authority and is rejected. A truly unprivileged nested rootless daemon would need a separate feasibility proof of nested user namespaces, subordinate ID mapping, cgroup delegation, storage and networking; no such proof is available. If separate rootless Engines cannot satisfy host-file isolation, core/runtime separation, independent runtime policy and egress denial, Docker-only remains blocked.

## Trusted IPC contracts (Codex #1 owns security semantics)

Compose network membership, a socket file's existence, static caller-supplied IDs, and shared bearer tokens alone are not verified peer identity. Use private Unix sockets in owner-controlled directories for approved host-service links, strict bounded/versioned schemas, and security tests. Container-to-host identity cannot be inferred from container UID translation. The current Docker-only candidate places Worker, Authorizer, Launcher and Runtime API Policy Gateway as separate host control services while Docker manages Core and synthetic workload containers. If the owner means every process must run inside Docker, this candidate fails and must be rejected. Do not add a direct Authorizer-to-Launcher channel.

### API → Authorizer

- **Status:** unresolved owner-to-Authorizer control channel; no Core socket mount or host peer mapping is selected. The proposed Authorizer revocation socket is not mounted into the API container. Owner revoke/cancel forwarding is unavailable, so real execution remains disabled.
- **Owner decision:** select a Docker-only-compatible channel and credential custody, or reject the host-service candidate if Docker-only excludes host control services. No token, container UID, network membership, or host-path convention substitutes for authenticated API identity.
- **Requirements after selection:** independently authenticate a purpose-bound request; use an explicit protocol version, request ID, operation enum, exact schema, maximum body/response sizes and deadlines; reject unknown versions/fields and malformed identity/context. Mutations use stable idempotency keys bound to actor, operation and request digest; reads reconcile uncertainty using the same key. Timeout, disconnect, malformed response, auth failure, stale service or DB failure denies new authority. No in-memory, permissive or network fallback.
- **Existing gap:** current API client sends `x-omnis-authorizer-token` over UDS. That implementation does not define the approved Docker-only host identity, owner-intent authorization or credential custody and is not the target channel contract.

### Worker → Launcher

- **Identity/channel:** private worker-to-launcher UDS; launcher authenticates kernel peer credentials mapped to the dedicated worker identity. Caller-provided `workerId` is a correlation claim only, not identity. No API or other container can open the socket; no TCP endpoint.
- **Request authority:** versioned bounded request identifies run, task, worker generation and idempotency key. Launcher independently reads/verifies durable current run lease, generation, authorization grant/consumption state, project/task binding and allowed mock operation before create/start. Worker input cannot select image, argv, environment, mount, network or resource policy.
- **Replay/duplicate:** unique launch operation key and durable state transition; same request returns current operation state, conflicting or stale generation denies. Enforce one launch attempt per authorization; lost response becomes `unknown`, reconciled by daemon labels/state, never automatic second create/start.
- **Cancellation/revocation:** Launcher and Runtime API Policy Gateway cannot stop, kill or cancel. Owner stop intent is persisted through the separately authenticated Authorizer path, then an independent stop-only terminator acts on the exact registered run/generation. Only its attestation, backed by actuator/kernel evidence that the complete process/helper scope is absent, establishes cancellation. Missing evidence, survivors or lost acknowledgement remain `UNKNOWN` and fenced; no timeout or retry frees the run for replay. Follow the controlling packet's C-1/C-2/R-03/N-2 ordering. The owner-to-Authorizer channel and M-4 trusted registration remain unresolved.
- **Recovery:** durable `requested → starting/unknown → running → terminal` state with explicit interrupted/recovery-required outcome; daemon loss or launcher restart does not convert unknown to not-started. Record daemon container ID/image digest and authorization generation. Audit without secrets.
- **Existing launch gap:** current UDS request carries `runId`, `workerId`, `generation`; launcher performs durable grant/lease checks. Source does not establish a kernel-authenticated peer identity contract or full launch uncertain-outcome protocol for the proposed rootless topology. Cancellation is not part of the Worker→Launcher contract; the target path is Authorizer intent plus the independent terminator, and both the owner channel and trusted registration remain unresolved.

### Launcher → Synthetic Runtime

- Launcher may request only a fixed `mock.execute` operation with schema-validated bounded input. Image is allowlisted by immutable digest; entrypoint and command fixed in launcher code/policy, never selected by request.
- Mount only a per-run empty scratch/workspace volume or narrowly scoped, validated read-only input plus writable scratch. Reject symlinks/path traversal, device mounts, host/Windows paths, Docker config, service sockets, `/proc`/host namespaces, credentials and environment passthrough.
- Runtime has no network (`network=none`), no daemon endpoint/socket, non-root UID, read-only root, `cap-drop=ALL`, `no-new-privileges`, seccomp/default policy, and measured CPU/memory/PID/time/output/disk limits. Verify actual effective settings under rootless Engine; do not assume requested flags took effect.
- Persist launch intent before daemon calls. If create/start/inspect/log responses are ambiguous, mark the launch outcome uncertain and inspect only by exact run ID and immutable labels; never issue a Launcher/daemon stop, kill or cancel operation, and prohibit automatic replay. Owner cancellation is handled only through the Authorizer and independent terminator path; its outcome remains `UNKNOWN` until exact-run terminator/actuator evidence is persisted. Preserve logs/events and terminal status without leaking input secrets.

## Windows → WSL2 local HTTPS ingress

The target ingress is one gateway container bound only to WSL IPv4 loopback `127.0.0.1:8443`; if IPv6 is enabled, bind only `::1` with an explicit equivalent policy. Never bind `0.0.0.0`, `::`, a WSL eth address, LAN address, or host network. No `netsh portproxy`, public tunnel, router forwarding or LAN access. Only gateway has a host-published port. API, authorizer, worker, PostgreSQL and launcher have no published host ports; PostgreSQL is not reachable from Windows except through the authenticated app API.

Terminate TLS in the gateway with a local leaf certificate whose SAN covers the canonical origin `https://localhost:8443` (and only additionally approved loopback names/addresses). The owner creates/trusts the local issuing CA in the Windows browser trust store; the CA private key stays offline/outside the distro and containers. The gateway receives only the leaf key/cert as a read-only, narrowly owned secret. No self-signed bypass or insecure-origin browser flags in owner use. Redirect HTTP to HTTPS only on loopback or refuse it. Exact API `OMNIS_ALLOWED_ORIGIN` is `https://localhost:8443`; reject alternate Host/Origin values.

WSL localhost forwarding behavior depends on WSL version and NAT vs mirrored mode. Microsoft documents localhost forwarding settings for WSL, but generic documentation does not prove local-only exposure on this owner's Windows build, WSL mode, Docker Engine, or firewall. Check both Windows and Linux listener tables; test Windows loopback positive access and a second LAN host negative access; inspect Hyper-V/Windows firewall policy and Docker's effective published bindings. Treat all of these as a separately authorized target acceptance requirement.

Gateway proxy policy is fixed upstreams only. Do not enable API framework trust-proxy or trust client-supplied `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, or `X-Forwarded-Proto`. Strip inbound forwarding headers; if a later reviewed proxy requires one, only the single gateway may set it and the API must accept it only on an authenticated private channel. Preserve browser `Origin` and cookies end-to-end, do not rewrite origin to an untrusted value, and verify host allowlists against request smuggling/alternate Host cases.

Session cookie requirement: `Secure; HttpOnly; SameSite=Strict; Path=/`, no `Domain` attribute, short configured lifetime and session-bound CSRF token. State-changing routes require exact allowed Origin plus valid CSRF token; cookie SameSite is defense in depth. If frontend flow requires weaker SameSite behavior, Codex #1 must approve the specific exception. Current signed sessions and CSRF code are in place, but session storage is process-local; API restart forces reauthentication, and multi-replica revocation is not established.

SSE uses same-origin authenticated cookies. Gateway must disable response buffering/compression for event streams, use suitable idle/read timeout and heartbeat behavior, preserve `Last-Event-ID`, and not cache streams. Every initial connection and reconnect rechecks the owner session and project/run authorization. Run-scoped SSE/replay exists. A distinct Mission Lane SSE endpoint does not. The gateway must not expose worker or database endpoints to make SSE function.

Static checks before packaging review: assert gateway bind address/port exactly loopback; reject other `ports`, `network_mode: host`, WSL/Windows paths, Docker socket outside launcher, DB/worker/API port publication, untrusted forwarded-header configuration, insecure-cookie setting, wildcard allowed origin, and TLS bypass flags; verify no `netsh portproxy` instructions. These checks prove configuration intent only, not effective WSL/firewall exposure.

## Secrets and backup ownership

### Current state (not acceptance)

Compose currently uses `env_file` host files for API and worker, and PostgreSQL receives its bootstrap password through environment substitution. Owner-only host file modes reduce who can read the source files, but `env_file` delivers values as process environment; it is not encrypted storage or a secret broker. No credential separation/rotation lifecycle for the new rootless topology is implemented. Current `pg_dump` produces a plaintext PostgreSQL custom archive and private JSON manifest with an unkeyed SHA-256 digest. The digest detects accidental mismatch only when expected metadata is trusted independently; it is not authentication/encryption. Restore tooling explicitly limits itself to operator-vetted archives. ADR-0010 remains Proposed; its encrypted/authenticated backup protocol is not implemented or accepted.

### Proposed ownership and delivery (Codex #1 security/crypto approval required)

- Owner controls the rootless service identity, application secret files, TLS leaf identity, backup destination, recovery identity and key-recovery procedure. Secrets are never committed, put in images, copied into runtime images, printed, included in diagnostic artifacts, or made visible to CI. CI receives synthetic test credentials only.
- Separate credentials and permissions: DB bootstrap/migration credential is provisioning-only; API, worker, authorizer, launcher and backup each receive distinct least-privilege credentials. Launcher/worker/runtime receive no DB superuser, TLS CA private key, backup decryption/signing key or provider credential. Synthetic runtime receives no secret.
- Replace `env_file` secret delivery in the proposed topology with owner-provisioned, read-only per-service secret files or another Codex #1-approved mechanism. Verify host ownership/mode and container UID/GID mapping; never rely on Compose network or filename as access control. Application code must explicitly read/validate secret files, and secret rotation/revocation must define restart, session invalidation and credential overlap windows.
- Define generated random keys, minimum entropy/format, ownership, access audit, rotation, revocation, expiry, emergency replacement, and behavior when key store is unavailable. Do not build a secret broker in this phase absent separate approval.
- Backup acceptance requires streaming authenticated encryption of archive **and** sensitive manifest, independent authentication/signature key, anti-rollback/freshness evidence, strict archive TOC allowlist, and complete cryptographic verification before plaintext is exposed to PostgreSQL. Use distinct backup-writer, decrypt/restore, and key-administration roles. Keep backup keys outside the database volume and outside the backup destination.
- Recovery after WSL distro loss requires owner-controlled recovery material available outside that distro (for example a separately approved offline or OS credential store), a documented trusted-key identity, and a rehearsed restore into a fresh isolated PostgreSQL target before cutover. No single-distro-only key. Define RPO, RTO, retention, backup frequency, and destruction policy with owner. ADR-0010's proposed requirements must be implemented and independently reviewed before any real agent data or production restore is accepted.
- Static checks: image/history/SBOM and Compose config scans for credentials; verify env-file removal from proposed Compose, per-service mount allowlist and modes, runtime environment/log/artifact redaction, no secret in synthetic image, no secret path in backups, and rotation/revocation documented. Target acceptance must inspect effective process environment/mounts and test denial as each actual UID.
