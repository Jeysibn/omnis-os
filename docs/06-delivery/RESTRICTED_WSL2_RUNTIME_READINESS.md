### Restricted bootstrap credential files

The database tools accept explicit owner-selected paths; they do not load repository `.env.*` files or inherit `OMNIS_*`, `PG*`, or `DATABASE_URL` process variables. Prepare three owner-owned regular files with mode `0600` or stricter and keep them outside the repository:

- `restricted-db-bootstrap.env`: `OMNIS_RESTRICTED_DEVELOPMENT=true`, `OMNIS_EXECUTION_MODE=disabled`, `OMNIS_RESTRICTED_COMPOSE_PROJECT=omnis-os-restricted-dev`, `OMNIS_RESTRICTED_DB_NAME=omnis_restricted_dev`, `OMNIS_RESTRICTED_PG_SYSTEM_IDENTIFIER`, `OMNIS_RESTRICTED_ADMIN_DATABASE_URL`, `OMNIS_RESTRICTED_MIGRATION_DATABASE_URL`, `OMNIS_RESTRICTED_MIGRATOR_PASSWORD`, and `OMNIS_RESTRICTED_RUNTIME_PASSWORD`.
- `restricted-worker.env`: `OMNIS_RUNTIME_DB_PASSWORD` matching the restricted runtime password. This is the same owner-approved Worker file used by the restricted profile. `OMNIS_INTERNAL_TOKEN` is permitted for the application profile but is not required by the database bootstrap tools. No Authorizer, launcher, provider, or migration/admin variables may be placed in application env files.
- `restricted-db-migration.env`: the restricted lock, project, database, system identifier, and `OMNIS_RESTRICTED_MIGRATION_DATABASE_URL` only. This file contains no administrative URL/password, runtime password, provider credentials, or Authorizer/launcher configuration.

Both URLs must explicitly target loopback port `5432` and database `omnis_restricted_dev`; the admin URL must use `omnis` and migration URL must use `omnis_migrator`. Passwords must be at least 64 hexadecimal characters and the migration URL password must match the explicit migration password. Values must be owner-supplied through the approved local secret custody process; this package does not generate, inspect, or approve credentials. The restricted preflight reads values in memory and prints only generic results or variable names.

The system identifier is read-only cluster metadata. After PostgreSQL starts under a separate exact-resource authorization, capture `Database system identifier` from `pg_controldata` inside the exact verified PostgreSQL container, and place that decimal value in both owner-controlled database files. The role command compares it with `pg_catalog.pg_control_system()` before any cluster-wide role mutation; the migration command repeats the comparison as `omnis_migrator`. That role receives only `EXECUTE` on this metadata function, not the `pg_monitor` role. The project value remains a scope guard, not proof by itself: separately bind the verified daemon, exact container ID, published loopback port, project-scoped volume, and SQL-reported database/role/system identity. If the binding is unavailable or ambiguous, do not run either mutating command.

Before any separately authorized database mutation, the proposed sequence is:

```sh
pnpm db:roles:restricted -- preflight \
  --bootstrap-env "$OMNIS_RESTRICTED_DB_BOOTSTRAP_ENV" \
  --worker-env "$OMNIS_RESTRICTED_WORKER_ENV_FILE"
pnpm db:roles:restricted -- roles \
  --bootstrap-env "$OMNIS_RESTRICTED_DB_BOOTSTRAP_ENV" \
  --worker-env "$OMNIS_RESTRICTED_WORKER_ENV_FILE"
pnpm db:migrate:restricted -- \
  --migration-env "$OMNIS_RESTRICTED_DB_MIGRATION_ENV"
```

The `preflight` command is configuration-only. The `roles` command checks the live database, administrative role, superuser status, and exact PostgreSQL system identifier before any mutation. It then requires all four application role names and `omnis`/`pgboss` schemas to be absent, plus validates timeout and membership state, before the first mutation. It then gives login/password credentials only to `omnis_migrator` and `omnis_runtime`; `omnis_authorizer` and `omnis_launcher` are created without login, passwords, or memberships solely to satisfy existing migration ACL references. The migration command reads only its minimal migration env file and verifies the live database, `omnis_migrator` identity, and the same system identifier before calling application or pg-boss migration code; it does not load administrative or runtime credentials. Missing, conflicting, unsupported, or unknown file values fail before a connection is created; a live target mismatch fails before migration SQL. A mismatch or SQL failure exits nonzero and withholds driver error detail; retain the exact volume for review and do not retry, reset, or remove it without a new resource-specific decision.

## 3. Mode-transition and inventory gate

Configuration changes do not terminate a prior mock-enabled Worker or its descendants. Before any transition to restricted mode, a separately authorized read-only inventory must:

1. Confirm the exact Docker context endpoint and daemon identity (name, daemon ID, server version, operating system/root directory metadata) and record UTC plus Asia/Manila observation time.
2. Inventory all daemon containers, projects, networks, volumes, and relevant images by IDs/names without inspecting environment values. Identify all Omnis/QA/backup/MoniKey and unrelated resources and mark them out of scope.
3. Identify every prior enabled Worker and execution consumer by exact container ID and effective mode evidence that does not disclose secrets. Identify exact synthetic fixture/workload IDs and map project/database URL pathname to launcher scope only from authoritative configuration/evidence.
4. Confirm each old enabled Worker and every descendant/fixture workload is stopped, then prove it absent or exited through authoritative process/daemon evidence. A changed Compose file, launcher shutdown, `--rm`, or Run status is insufficient. If scope mapping is ambiguous or any survivor is unknown, stop and quarantine; do not broaden cleanup.
5. Confirm the proposed project, volume, networks, database name, and ports are unused and do not select any existing resource. Any collision means stop and owner decision; do not rename or remove existing resources to proceed.

Inventory commands such as `docker --context "$CTX" info`, `ps -a`, `network ls`, `volume ls`, and `image ls` are future read-only examples only. They have not been run and still target a selected daemon, so the owner must separately authorize the exact context and read-only inventory scope. Never run `docker inspect` with unfiltered environment output or print `docker compose config` output containing values.

## 5. PostgreSQL provisioning and recovery boundary

Intended order is: create a fresh project-scoped PostgreSQL volume; wait for PostgreSQL health; run restricted configuration preflight; provision login roles `omnis_migrator` and `omnis_runtime` plus inert `NOLOGIN` ACL principals `omnis_authorizer` and `omnis_launcher` with the administrative connection; verify live database, current user, superuser status, and PostgreSQL system identifier before any role-changing SQL; require all four role names and application schemas to be absent; apply migrations as `omnis_migrator` only after a second live identity check; verify migration ledger and database identity; only then start API/Worker/Web. No DB operation runs automatically as a Compose service command.

The legacy `db:roles` and `db:migrate` commands retain their existing mock-enabled behavior and shared env-file conventions. They are not the restricted startup path. The new restricted commands require explicit env-file paths, reject unknown keys and inherited connection/mode variables, require the exact database and captured PostgreSQL system identifier, and have no `omnis` fallback. Migration role names referenced by legacy SQL are provisioned as `NOLOGIN` ACL principals without credentials. They are proposed source-level procedures only: independent review and separate owner authorization are still required before any database mutation.

The existing migration runner is not transactional as a whole: it applies ordered/checksummed app migrations, starts PgBoss migration/queue setup, then grants pg-boss access. On a partial failure, retain the exact volume and collect sanitized failure evidence; do not infer rollback or retry blindly. A fresh project volume and a reviewed recovery/backup choice are prerequisites. No local DB content was read.

PostgreSQL currently relies on pinned image defaults for startup/runtime UID and privileges. Before startup, require image metadata and an independent compatibility decision for initialization-time root behavior, steady-state `postgres` UID, capabilities, read-only-rootfs feasibility, and numeric CPU/memory/PID bounds. No UID or limits are invented here.

## 7. Evidence, incident response, and retention

Before operations, owner must name an operator, authorization window, recovery contact, evidence location, and retention period. Capture:

- Source commit, script versions, Compose file order, sanitized `config --quiet` result, env-file names/mode/owner and preflight verdict (never contents or values).
- Docker context endpoint metadata, daemon ID/name/version/OS, and exact container/image/network/volume IDs before and after.
- Image digests and PostgreSQL image `Config.User`; actual service user, capability/security options, resource limits, mounts, networks, and port bindings.
- Health status, non-secret capability JSON fields, expected HTTP statuses, bounded sanitized logs, request identifiers only where non-sensitive, DB identity (`current_database`, `current_user`) and migration head without row data.
