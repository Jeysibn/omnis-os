## Corrected candidate trust architecture — design only

The following closes the review ambiguity in the design. It specifies a candidate to review; it does not create or authorize services.

### Gateway provisioning and identity

- The Runtime API Policy Gateway is a **host system service**, never a container controlled by either Docker Engine. Root/systemd is a trusted host-provisioning authority only if the owner explicitly accepts host root and the signing/update chain in the trust base.
- Proposed service identity: dedicated non-login `omnis-runtime-gateway` UID/GID, distinct from the `omnis-runtime-engine` and `omnis-runtime-launcher` host identities and outside both engines' subordinate UID/GID ranges. The Gateway has no database credential, no shell, no provider credential, no host-home access and no Engine-admin group.
- A root-managed Runtime Engine system unit runs rootless as `omnis-runtime-engine` with `Delegate=yes`. The proposed path is `/run/omnis/runtime-engine/docker.sock`: `/run/omnis` is root-owned/non-writable; its `runtime-engine` child is owned by the dedicated Engine UID, traversable by the Gateway group, and not accessible to launcher/Core identities; the socket is Engine-owned, mode `0660`, with a Gateway-only client group. Only the Gateway is an authorized **client**; the Engine daemon itself necessarily owns the listener and has full authority over its Engine. It is a trusted computing base component, and Gateway policy does not constrain a compromised daemon. If the owner requires containment of a compromised daemon, this architecture is blocked and needs a stronger isolation boundary such as a separately disposable VM. The socket is not mounted into any container.
- Proposed launcher→Gateway UDS: root-created non-writable parent directory, exact launcher-only group traversal, socket owned by Gateway and that group, mode `0660`. `SO_PEERCRED` must match the single dedicated host launcher UID. The launcher receives only this typed UDS, never a Runtime Engine socket, alternate context, TCP endpoint, inherited descriptor or gateway update control.
- Core Engine UID maps must not map a container identity to the launcher UID. Otherwise Core Engine authority can impersonate the UDS peer and this identity boundary is **BLOCKED**. Container identity/name is not peer authentication.
- The Engine-owned socket directory means a compromised Engine UID can replace its own socket path; this is within the explicitly trusted Runtime Engine TCB. No launcher/Core/Runtime-workload UID may write or replace any Gateway-facing path. Tests must inspect every path component, owner/mode/inode and symlink behavior and attempt substitution as each untrusted identity; the Runtime Engine UID result is reported as the stated trust assumption, not a gateway containment pass.
- Binary, systemd unit, trust anchors, policy and daemon configuration are root-owned and non-writable by Gateway, launcher and either Engine. The Gateway reads a signed/pinned policy/config digest from a root-owned directory; the small journal is in a separate Gateway-writable, launcher-inaccessible state directory. Policy updates use an owner-approved, signature-verified package and an atomic integrity check. Only the trusted host provisioner/root system manager may install, rollback or restart it. There is no Docker-driven update path or self-update.
- Candidate unit hardening includes `NoNewPrivileges=yes`, empty ambient/capability sets, `ProtectSystem=strict`, `ProtectHome=yes`, private tmp/devices, restricted syscalls, `RestrictAddressFamilies=AF_UNIX`, and `IPAddressDeny=any`. Whether each setting is supported and effective on the selected Linux/WSL build must be inspected and tested; listing it is not enforcement evidence. The Gateway parser should be memory-safe and treat daemon/workload output as bounded opaque bytes.

### Authorization authorities and consume order

| Field/state                                                                                               | Authoritative owner                                                                                                               | Gateway's allowed evidence path                                                                                                                                                     |
| --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner approval and permitted runtime/model/tool-free profile                                              | Authenticated owner API + Authorizer                                                                                              | Signed assertion from the Authorizer; Gateway does not trust launcher claims or read the Core DB.                                                                                   |
| Task/project/run and persisted authorization state                                                        | Core database through Authorizer's restricted DB role                                                                             | A narrow typed Authorizer status/revocation UDS query. No DB URL/password or SQL connection is provided to Gateway.                                                                 |
| Worker identity, active lease and generation                                                              | Worker-authenticated intent reconciled against authoritative DB lease state by Authorizer                                         | Signed operation assertion plus current Authorizer verdict; `workerId` supplied by launcher alone is not authoritative.                                                             |
| Run operation, operation ID, request/prompt digest, runtime image, restrictions, limits and policy digest | Worker supplies immutable intent; Authorizer validates task/run/owner state; root-owned policy fixes allowed image/profile/limits | Capability binds all values; Gateway recomputes request digest and compares to the signed claims and pinned root-owned policy. Caller fields never select Engine paths or defaults. |
| `iss`, `aud`, `sub`, `kid`, `jti`, not-before/expiry                                                      | Authorizer signing authority and Gateway's root-owned key registry/clock policy                                                   | Strict signature verification with exact issuer/audience/key ID, revocation lookup and bounded expiry. Unknown key or unavailable state denies.                                     |
| One-use consumption and dispatch outcome                                                                  | Gateway-owned durable journal; Engine inspect/labels are evidence for reconciliation only                                         | Atomic unique consume before dispatch; raw Engine state cannot mint a second permit.                                                                                                |

Future real-runtime issuance is owner-authorized only. The Authorizer must validate owner session, exact Task/Project/latest Run, approved runtime/model identity and empty tool scope; confirm worker-authenticated intent and current DB lease/generation; then issue a short-lived, operation-specific signed capability. A separate private status/revocation UDS lets the Gateway confirm current authorization and lease state before each operation without giving the Gateway a cross-Engine database credential. Failure or staleness denies. The current `omnis_launcher` `EXECUTE` grant is retained only for the existing mock path until a separately reviewed backend migration; a real-runtime path must not reuse it to issue or consume live authority.

Required order: (1) strict frame/schema and peer UID; (2) signature, exact `kid`/issuer/audience, field/request/prompt binding, policy digest and time checks; (3) current Authorizer allow/revocation/lease verdict; (4) atomic durable consume keyed by `jti` and operation ID with exact request hash; (5) flush/fsync durable state; (6) construct one fixed complete Engine request; (7) persist `dispatch-attempted` for the step and fsync it **before writing any socket bytes**; (8) send that step once; (9) persist bounded response/outcome and audit state. A capability authorizes one immutable bounded operation sequence, not arbitrary Engine API calls. Journal each step separately as `intent-durable → dispatch-attempted-durable → response-durable`; no mutating step is retried after ambiguous dispatch. Concurrent duplicate consume must have one winner. No Engine bytes are sent before both operation consume and that step's dispatch marker commit.

Crash before durable consume commit means no dispatch is permitted. Crash after consume or after a per-step dispatch marker commits—before socket write, during write, after daemon acceptance or before response/audit—makes that sequence/step `unknown`; the same mutating step is never redispatched. The marker must be durable before bytes are written; a crash in the marker-to-write window is conservatively quarantined even when no write is known. If a preceding step has a durable success response, only the next fixed step may proceed. Restart closes admission, checks policy/binary/journal integrity and queries the Authorizer, then performs read-only exact-label/container reconciliation. A matching resource is reconciled; missing/ambiguous evidence stays quarantined `unknown`. Starting again requires a fresh owner authorization and a separately proven fence that the old attempt cannot still execute; no automatic retry or replay.

The existing launcher DB grant was source-checked, not queried from a live database. The future VM fixture must verify effective `has_function_privilege` and routine ACLs for all service roles, test denied caller substitution, and prove Gateway has no Core DB credential. This PR does not change migrations or backend authorization code.

### Independent egress candidates

The default is no Runtime workload IP egress. Two host-controlled candidates are specified for later testing, not selected as verified controls:

1. Root-owned host-network-namespace nftables output policy matching the dedicated Runtime Engine UID (`meta skuid`), covering IPv4 and IPv6, DNS, TCP/UDP, loopback, link-local, bridge/Core/Windows/WSL addresses and all other destinations. Rules are provisioned outside the Engine user/network namespace; Engine/Gateway UDS traffic stays AF_UNIX. Verify that every RootlessKit/slirp4netns/pasta/gvisor-tap-vsock and port helper socket is attributable to the constrained identity; any helper under another UID is a bypass until separately confined.
2. A root-owned system-level systemd unit/cgroup policy with `IPAddressDeny=any` applying to the Runtime daemon and descendants. Its BPF/cgroup availability and propagation through `Delegate=yes` must be verified on the exact OS. Docker's own network flags or rules inside daemon-controlled namespaces are not independent enforcement.

The VM plan tests each candidate with private dummy-sink positive controls on the exact same route/helper, host-loopback/IPv4/IPv6/DNS/proxy/DoH negatives, daemon attempts to alter its own namespace, alternate networks/host mode/publish/direct IP, and observable host firewall/cgroup counters. No public endpoint is used. A fake recorder or an unreachable destination without an observed counter is inconclusive. Owner/security must approve which candidate and trust assumption to test; default-deny remains unverified until then.

### Independent termination and recovery

The candidate Runtime Engine is supervised by the **system** systemd manager, not its `systemd --user` instance: root-owned unit, `User=omnis-runtime-engine`, `Delegate=yes`, explicit CPU/memory/task bounds, `RuntimeMaxSec`, `KillMode=control-group`, `Restart=no`, and live-restore disabled. A separately reviewed host terminator is required for per-run cancellation; it must accept only a signed `(run_id, generation, operation_id)` on a narrow local interface, map it to an exact registered cgroup/resource identity, send TERM then bounded KILL, and verify no process survives. It exposes no shell, arbitrary PID/path, Docker API or wildcard cleanup. Exact owner-labelled resource manifests prevent cross-run removal.

System-manager ownership and a future terminator are not implemented. Hypervisor-controlled destruction of the exact named no-uplink disposable Linux VM is an independent final environment terminator for VM-stage cleanup and may recover from a failed test. It does **not** prove in-guest/per-run kill behavior or that container removal killed escaped helpers; those tests need system-manager/cgroup evidence before the VM is destroyed. WSL distro termination is not a substitute for a tested in-guest terminator. Missing manager, journal, boot-ID fence or exact ownership keeps admission closed and state quarantined. No broad prune or automatic restart/replay.
