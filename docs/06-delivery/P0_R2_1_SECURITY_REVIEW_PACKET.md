Rootless mode limits daemon host privilege; it does not make a compromised daemon safe from its own Engine authority. No document may call the Gateway independent of the daemon while packaging it under that daemon.

## Worker identity and trusted intent

Authorizer authenticates the Worker at the Worker→Authorizer UDS using `SO_PEERCRED` exact host UID/GID plus the protected socket path. `workerId` is a database lease label and request metadata only; it is never identity evidence. Authorizer binds authenticated service identity to the authoritative `(task_id, project_id, run_id, generation, lease_owner, lease_expiry, task_revision, authorization_revision)` read from its restricted DB role. Worker cannot assert or override lease ownership. It must prove current lease ownership by matching DB state; generation is a fencing token. Each intent carries unique request nonce and operation ID, and Authorizer rejects duplicate, expired, revoked, superseded, wrong-task, wrong-project, wrong-run or wrong-generation intents. Replay state is durable and unique by issuer, nonce, operation and step.

The trust base includes host root/systemd, kernel peer credentials, immutable Worker executable/config and the DB lease authority. The Core Engine cannot impersonate `omnis-worker`: its subordinate ranges exclude the service UID and it has no Worker socket mount. A compromised Worker can request work only under its own active lease and owner grant; it remains trusted to form task intent. If peer credentials, socket ownership, DB lease state, task binding, nonce store, or trusted clock is unavailable or inconsistent, Authorizer denies issuance and Gateway denies dispatch. Synthetic negative fixtures must spoof `workerId`, connect from launcher/Core/runtime UIDs, replace socket paths, pass inherited FDs, replay nonce, and mix task/run/generation/lease values; all must yield zero Engine dispatch.

## Authorization, revocation, dispatch, and payload binding

There is no atomic transaction spanning the Authorizer database and Docker Engine. The decision linearizes at the durable Authorizer reservation transaction for one specific Engine mutation step. All owner revocation, lease renew/supersession, and step reservation operations serialize on the same authorization/run row (or equivalent serializable transaction and compare-and-swap revision). Each reservation checks current owner status, run status, authorization revision, worker lease owner/generation/expiry, operation ID, exact request digest and step index, then atomically records unique consumed nonce, expected revision/generation and reservation result. Only after commit may Authorizer sign a one-step ticket bound to that reservation. Gateway verifies the signature, issuer/audience/key ID, expiry, exact revision/generation, digest and step, then durably consumes its local journal entry before writing any Engine request bytes. No ticket authorizes a second mutation or a retry.

Race outcomes are normative:

| Race point                                                                              | Winner and required result                                                                                                                                                                                                                                                                                                                 |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Revocation or lease supersession commits before reservation transaction                 | Revocation/new generation wins; reservation fails; no ticket and no Engine dispatch.                                                                                                                                                                                                                                                       |
| Reservation transaction commits before revocation/lease supersession                    | The reservation wins for this one exact mutation step. A later revocation cannot retroactively revoke a committed ticket; it blocks reservation of every later step. This is the linearization rule that removes an unprotected status-check/dispatch interval.                                                                            |
| Gateway local consume commits, then process crashes before any Engine bytes             | The step was already reserved and locally consumed; outcome is `unknown`; no automatic retry. Read-only reconciliation and independent termination evidence are required. Later steps remain blocked by revocation or uncertainty.                                                                                                         |
| Engine create succeeds, then revocation/lease loss occurs before start reservation      | Create step remains recorded. Start reservation rechecks current revision/generation and is denied. Exact created object is inert/quarantined and externally terminated; no start.                                                                                                                                                         |
| Engine create/start request is sent but response is lost, malformed, or process crashes | Step outcome is `unknown`, even if Engine inspect suggests absence. No resend or duplicate create/start; reconcile read-only and preserve unknown until independent evidence resolves it.                                                                                                                                                  |
| Gateway or Authorizer restarts                                                          | Admission remains closed until journal/anchor, DB revision/lease state, exact Engine labels, process/cgroup ownership and stale-operation set reconcile. No automatic replay.                                                                                                                                                              |
| Status/revocation/DB/clock verification fails or is stale before reservation            | Reject before reservation. After reservation, ticket signature, audience, expiry, digest and reservation revision are verified locally; no separate check-then-act status query is treated as authoritative. If Gateway cannot verify or durably consume ticket, do not dispatch; retain reservation as consumed/unknown and deny retries. |

For each multi-step launch (`create`, then `start`, then bounded `inspect/output`), a distinct one-step reservation is required, and each step revalidates current authorization revision and lease fence. A revoked or superseded operation cannot request a later ticket. Engine state is evidence, not authority. The system must not claim cross-database/Engine atomicity.

The exact runtime input is produced from an authoritative immutable task/profile revision by Worker and submitted byte-for-byte to Authorizer for digesting. Hash input is unambiguous: `SHA-256(ASCII("OMNIS-OS-RUNTIME-PAYLOAD") || 0x00 || uint16_be(payload_profile_version) || JCS({task_revision, profile_revision, run_id, generation, byte_length, payload_b64url}))`; `payload_b64url` is canonical unpadded base64url encoding of the exact payload bytes, with decode/re-encode identity required. Thus JSON wrapper key order/whitespace is canonicalized by the pinned RFC 8785 profile, but payload bytes—including payload JSON whitespace, Unicode normalization form and line endings—are bound exactly and never normalized. Authorizer signs the digest and metadata. Payload travels Worker→Launcher→Gateway as opaque bounded bytes; the compromised Launcher is untrusted transport. Gateway hashes received bytes, checks exact length and signed digest, then stages those same bytes read-only for the synthetic runtime. No re-rendering or substitution occurs after authorization. Use the existing synthetic broker request ceiling of **65,536 bytes** as the design maximum; reject larger payloads before reservation. Unknown profile version, digest mismatch, modified/truncated/substituted bytes, unavailable authoritative payload, or profile/task revision mismatch yields zero Engine dispatch. No active provider connector is introduced. Negative fixtures alter one byte, Unicode sequence, JSON whitespace in payload, task/profile revision, run/generation, length, truncate/oversize and substitute another run's payload.

## Durable journal and restart admission fence

Authorizer's transactional, monotonic reservation ledger is the external one-use authority; a Gateway-local append-only journal is additional evidence, not a second independent issuer. Each record binds boot/instance epoch, monotonically increasing sequence, previous-record hash, `jti`, operation/step, request digest, authorization/lease revision, dispatch marker and response classification. Only one Gateway process may own a journal: systemd singleton plus exclusive `flock` held on a root-owned directory and a file lock; a second process must fail startup before binding UDS. Journal file is Gateway-writable only; directory, unit, binary and policy are provisioner-owned.

Before any Engine bytes, append the consumed/reserved record and dispatch-attempt marker, `fdatasync`/`fsync` the file, then `fsync` the containing directory for newly created/renamed records; only then issue the request. After response, append and sync the classified result. This ordering is a design requirement, not a claim that a particular filesystem, virtual disk cache, VHDX, or hypervisor honors power-loss durability. Feasibility evidence must record filesystem/mount/barrier/cache configuration and perform abrupt guest and externally controlled VM power-loss cases. Process-kill hooks alone do not prove power-loss durability.

Missing, corrupted, ambiguous, older-than-external-high-water, hash-chain-mismatched or snapshot-rolled-back journal closes admission. Multiple writer detection also closes admission. Restoring a VM snapshot never restores authority: Authorizer's external monotonic high-water/instance epoch must reject stale journal state and issue a fresh epoch only after review. Reopen requires independent evidence of current external anchor and DB revisions, intact signed binaries/policy, one Gateway writer, exact read-only Engine reconciliation, no surviving unowned process/cgroup, current revocation/lease check, and an independent terminator able to bound any stale execution. Unknown outcomes remain quarantined; no missing object authorizes replay.

## Egress and termination enforcement candidates

Egress is not enforced by Runtime Engine configuration alone. Candidates to test independently are a host-owned network namespace and nftables policy around the daemon and all RootlessKit/slirp4netns/pasta helpers; systemd cgroup-v2/BPF restrictions where the selected kernel/systemd actually supports them; and a no-uplink private VM network with hypervisor firewall as an outer boundary. Each must be measured for IPv4, IPv6, DNS, loopback, AF_UNIX, AF_VSOCK/Hyper-V sockets where exposed, Windows interop, automount, D-Bus/varlink and every accessible daemon socket. Record kernel features, nftables hooks/priority/counters, cgroup-BPF attachment, namespace/process/FD inventory and the exact enforcing point. A missing route or unreachable sink is inconclusive. Same-path positive, denied, restored-positive controls are required; no public endpoint is used.

Termination authority must be outside Worker, Launcher, Gateway and Runtime Engine: a root-owned system manager plus separately provisioned terminator controls an exact Runtime service/run cgroup, fixed deadline and startup fence. `RuntimeMaxSec`/`KillMode=control-group` bound the whole daemon service tree only; they are not per-run termination. Prove dockerd, RootlessKit, containerd/shim, container process and helper descendants occupy the intended unit/cgroup and that cgroup kill reaches each while Gateway and daemon APIs are unavailable. Restart is `no`; startup stays fenced until stale state reconciles; exact resource ownership is required for cleanup. Hypervisor destruction is sufficient only as final destruction of the disposable VM and disk after in-guest evidence collection. It is not proof of bounded per-run termination or a PASS for active-workload termination.

## Corrected candidate trust architecture — design only

The following closes the review ambiguity in the design. It specifies a candidate to review; it does not create or authorize services.

### Gateway provisioning and identity

- The Runtime API Policy Gateway is a **host system service**, never a container controlled by either Docker Engine. Root/systemd is a trusted host-provisioning authority only if the owner explicitly accepts host root and the signing/update chain in the trust base.
- Proposed service identity: dedicated non-login `omnis-runtime-gateway` UID/GID, distinct from the `omnis-runtime-engine` and `omnis-runtime-launcher` host identities and outside both engines' subordinate UID/GID ranges. The Gateway has no database credential, no shell, no provider credential, no host-home access and no Engine-admin group.
- A root-managed Runtime Engine system unit runs rootless as `omnis-runtime-engine` with `Delegate=yes`. The proposed path is `/run/omnis/runtime-engine/docker.sock`: `/run/omnis` is root-owned/non-writable; its `runtime-engine` child is owned by the dedicated Engine UID, traversable by the Gateway group, and not accessible to launcher/Core identities; the socket is Engine-owned, mode `0660`, with a Gateway-only client group. Only the Gateway is an authorized **client**; the Engine daemon itself necessarily owns the listener and has full authority over its Engine. It is a trusted computing base component, and Gateway policy does not constrain a compromised daemon. If the owner requires containment of a compromised daemon, this architecture is blocked and needs a stronger isolation boundary such as a separately disposable VM. The socket is not mounted into any container.
- Proposed launcher→Gateway UDS: root-created non-writable parent directory, exact launcher-only group traversal, socket owned by Gateway and that group, mode `0660`. `SO_PEERCRED` must match the single dedicated host launcher UID. The launcher receives only this typed UDS, never a Runtime Engine socket, alternate context, TCP endpoint, inherited descriptor or gateway update control.
- Core Engine UID maps must not map a container identity to the launcher UID. Otherwise Core Engine authority can impersonate the UDS peer and this identity boundary is **BLOCKED**. Container identity/name is not peer authentication.
- The Engine-owned socket directory means a compromised Engine UID can replace its own socket path; this is within the explicitly trusted Runtime Engine TCB. No launcher/Core/Runtime-workload UID may write or replace any Gateway-facing path. Tests must inspect every path component, owner/mode/inode and symlink behavior and attempt substitution as each untrusted identity; the Runtime Engine UID result is reported as the stated trust assumption, not a gateway containment pass.
- Binary, systemd unit, trust anchors, policy and daemon configuration are root-owned and non-writable by Gateway, launcher and either Engine. The Gateway reads a signed/pinned policy/config digest from a root-owned directory; the small journal is in a separate Gateway-writable, launcher-inaccessible state directory. Policy updates use an owner-approved, signature-verified package and an atomic integrity check. Only the trusted host provisioner/root system manager may install, rollback or restart it. There is no Docker-driven update path or self-update.
- Candidate unit hardening includes `NoNewPrivileges=yes`, empty ambient/capability sets, `ProtectSystem=strict`, `ProtectHome=yes`, private tmp/devices, restricted syscalls, `RestrictAddressFamilies=AF_UNIX`, and `IPAddressDeny=any`. Whether each setting is supported and effective on the selected Linux/WSL build must be inspected and tested; listing it is not enforcement evidence. The Gateway parser should be memory-safe and treat daemon/workload output as bounded opaque bytes.

Future real-runtime issuance is owner-authorized only. For every Engine mutation step, the Authorizer validates owner session, exact Task/Project/latest Run, approved runtime/model identity and empty tool scope; authenticates the Worker peer; and serializes current DB lease/generation/revocation state with the one-step reservation. It then issues a short-lived, nonce-bound signed ticket with key ID, revision, generation, request digest and step. Launcher and Gateway are separate host services, not Core containers. Gateway uses a private Authorizer UDS for signed-ticket verification/reconciliation; this does not create an unprotected check-then-act decision because the DB reservation commit is the linearization point and authorizes only that exact step. A revocation committed first denies the step; one committed after reservation blocks subsequent steps but does not retroactively undo the reserved mutation. The current `omnis_launcher` `EXECUTE` grant is retained only for the existing mock path until a separately reviewed backend migration; a real-runtime path must not reuse it to issue or consume live authority.

The normative serialized reservation, consume/dispatch state machine, race outcomes, payload binding and crash behavior are defined in the controlling ‘Authorization, revocation, dispatch, and payload binding’ section above. No earlier order permits status-check/act without a durable one-step reservation.

The existing launcher DB grant was source-checked, not queried from a live database. The future VM fixture must verify effective `has_function_privilege` and routine ACLs for all service roles, test denied caller substitution, and prove Gateway has no Core DB credential. This PR does not change migrations or backend authorization code.

### Independent termination and recovery

The candidate Runtime Engine is supervised by the **system** systemd manager, not its `systemd --user` instance: root-owned unit, `User=omnis-runtime-engine`, `Delegate=yes`, explicit CPU/memory/task bounds, `RuntimeMaxSec`, `KillMode=control-group`, `Restart=no`, and live-restore disabled. A separately reviewed host terminator is required for per-run cancellation; it must accept only a signed `(run_id, generation, operation_id)` on a narrow local interface, map it to an exact registered cgroup/resource identity, send TERM then bounded KILL, and verify no process survives. It exposes no shell, arbitrary PID/path, Docker API or wildcard cleanup. Exact owner-labelled resource manifests prevent cross-run removal.

System-manager ownership and a future terminator are not implemented. Hypervisor-controlled destruction of the exact named no-uplink disposable Linux VM is an independent final environment terminator for VM-stage cleanup and may recover from a failed test. It does **not** prove in-guest/per-run kill behavior or that container removal killed escaped helpers; those tests need system-manager/cgroup evidence before the VM is destroyed. WSL distro termination is not a substitute for a tested in-guest terminator. Missing manager, journal, boot-ID fence or exact ownership keeps admission closed and state quarantined. No broad prune or automatic restart/replay.
