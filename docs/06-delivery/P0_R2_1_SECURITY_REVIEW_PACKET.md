## Worker identity and trusted intent

Authorizer authenticates the Worker at the Worker→Authorizer UDS using `SO_PEERCRED` exact host UID/GID plus the protected socket path. `workerId` is a database lease label and request metadata only; it is never identity evidence. Authorizer binds authenticated service identity to the authoritative `(task_id, project_id, run_id, generation, lease_owner, lease_expiry, task_revision, authorization_revision)` read from its restricted DB role. Worker cannot assert or override lease ownership. It must prove current lease ownership by matching DB state; generation is a fencing token. Each intent carries unique request nonce and operation ID, and Authorizer rejects duplicate, expired, revoked, superseded, wrong-task, wrong-project, wrong-run or wrong-generation intents. Replay state is durable and unique by issuer, nonce, operation and step.

The trust base includes host root/systemd, kernel peer credentials, immutable Worker executable/config and the DB lease authority. The Core Engine cannot impersonate `omnis-worker`: its subordinate ranges exclude the service UID and it has no Worker socket mount. A compromised Worker can request work only under its own active lease and owner grant; it remains trusted to form task intent. If peer credentials, socket ownership, DB lease state, task binding, nonce store, or trusted clock is unavailable or inconsistent, Authorizer denies issuance and Gateway denies dispatch. Synthetic negative fixtures must spoof `workerId`, connect from launcher/Core/runtime UIDs, replace socket paths, pass inherited FDs, replay nonce, and mix task/run/generation/lease values; all must yield zero Engine dispatch.

## Versioned per-step authorization and input contract — design only

Version 1 proposals in the P0-R2.2 plan are superseded where they omit the fields and state transitions below. This is a future contract only; production protocol code is unchanged. One immutable operation has a canonical `operation_id`; `step_index` starts at 0 for `create` and increases by exactly one for each following ticketed step, including read-only `inspect`, `read_output` and `reconcile`; the Authorizer maintains the authoritative expected next index and rejects skips/reordering. Each has an exact `step_type` (`create`, `start`, `inspect`, `read_output`, or `reconcile`). Mutation steps `create` and `start` each require a separate one-use ticket. Read-only `inspect`/`read_output`/`reconcile` use distinct one-use read tickets and can never mutate or recreate. `cancel` is not an ordinary operation ticket or Gateway operation; a separate stop-socket response is bound to the exact run/generation and stop ID. The proposed maximum execution-ticket lifetime is 30 seconds, subject to Codex #1 approval; clock uncertainty rejects.

Each signed ticket binds: `protocol_version`; `operation_id`; `step_index`; `step_type`; `reservation_id` and monotonic `reservation_revision`; `authorization_id` and `authorization_revision`; `task_id`/`task_revision`; `profile_id`/`profile_revision`; `project_id`; `run_id`; `execution_generation`; `lease_id`, `lease_owner` and `lease_revision`; exact `input_profile_version`, `input_digest` and `input_length` (zero/null only for operations that do not consume input); policy digest/restrictions; `iss`, `aud`, and peer subject derived from kernel credentials; `jti` one-use ticket ID; `not_before`; `expires_at`; and a bounded operation request digest. IDs/revisions are typed, canonical and non-path values. A ticket is valid only for the exact next expected step, tuple and payload, at the exact policy and lease revisions. A one-step ticket cannot authorize another step, another payload, retry dispatch, or another peer. TTL has a fixed reviewed upper ceiling; clock uncertainty, expiry boundary ambiguity, unknown key or unavailable revocation/lease state denies before consume. Exact numeric TTL and clock rules remain an implementation/security decision.

### Worker → Authorizer → Launcher → Gateway flow

1. Worker obtains task/profile/run/generation and lease evidence from its authenticated service context; it does not accept caller `workerId` as authentication. Worker connects directly to Authorizer over the protected UDS. Authorizer checks exact host `SO_PEERCRED`, current owner authorization, task/profile revisions, active lease owner/revision/expiry, generation, operation ordering and unique Worker intent nonce against authoritative state.
2. Worker submits the exact immutable payload bytes (or an authenticated immutable object reference whose fetched bytes are re-hashed) to Authorizer with task/profile/run/generation. Authorizer obtains or verifies the authoritative payload itself; a digest supplied only by Worker/Launcher is insufficient. It enforces the 65,536-byte maximum and computes the domain-separated payload digest over exact bytes plus payload profile version, revisions, run and generation.
3. Worker requests the initial ticket for the next step from Authorizer. Authorizer authenticates Worker by exact host peer UID/GID, serializes the request with revocation and lease changes, commits a unique reservation row, then signs the ticket. Authorizer returns that signed ticket and reservation receipt to the authenticated Worker; Worker forwards them to Launcher over the Worker→Launcher UDS, whose receiver independently checks exact host peer UID/GID. The Launcher does not become an issuer or ticket requester; launcher-supplied `workerId` remains metadata only.
4. Launcher is the caller that transports the ticket and opaque input bytes to Gateway. Launcher cannot request or mint the next ticket. After a step reaches a known terminal/reconciled state, the authenticated Worker requests the next ticket directly from Authorizer using the same operation ID plus next step index and a fresh intent nonce. Authorizer checks prior-step state, same task/profile/input tuple, current lease/revisions and authorization. This prevents Launcher-controlled step advancement.
5. Gateway verifies Launcher `SO_PEERCRED`, issuer/key/audience, subject, all revisions, expected step index/type, operation/request digest, expiry, restrictions and exact input length/digest. It durably consumes the ticket before any Engine request byte. For `create`, Gateway stages exactly the verified bytes read-only and reconstructs a fixed image/command request. `start` is a separate reservation after `create` is reconciled as the exact inert object. `inspect` and `reconcile` are read-only and never imply absence is permission to recreate. Each read query has bounded output, fresh request/ticket identity and no raw daemon identifiers. Unknown or mismatched state stays quarantined.

Authorizer reservation state follows the controlling C-1 contract: `RESERVED → CONSUMED → DISPATCHED → ACKNOWLEDGED | UNKNOWN` with a unique constraint over issuer plus `jti`, operation and step, and a serialized expected-step revision. A competing consume/reservation loses and returns `REPLAY_CONFLICT`; it cannot dispatch. The gateway journal transition is `ticket_verified → consume_fsynced → dispatch_attempted → known_result | unknown`. Durable consume precedes writing Engine bytes. A crash after consume and before/within dispatch is `unknown`; never reissue that step or infer “not executed” from a missing object. Reconciliation is read-only and independent termination is used if the effect cannot be bounded.

Revocation and lease supersession serialize against the anchor pre-fence and each ticket's durable `CONSUMED` receipt. If the pre-fence wins before the receipt commits, a ticket still in `RESERVED` is denied consumption and cannot dispatch. If the matching `CONSUMED` receipt commits first, that exact step may proceed once through a later dispatch attempt despite subsequent revocation; the receipt cannot authorize another step or retry. Ticket issuance into `RESERVED` alone does not survive a pre-fence. A later revocation prevents subsequent tickets and raises a stop request. A create that commits before a start ticket is denied remains inert and must be stopped/quarantined. No atomicity across DB and Engine is claimed. Gateway/Authorizer restart starts fenced; status, DB, signature, clock, journal or anchor uncertainty denies new tickets.

Negative Stage A fixtures must prove zero dispatch for: one-byte, whitespace, Unicode and cross-run payload substitution; mismatched digest/length or unavailable reference; stale authorization/task/profile/lease/reservation revision; wrong step index/type/order; expired/future/clock-uncertain ticket; wrong peer/audience/issuer/key; duplicate ticket; concurrent duplicate consumption; launcher attempt to request a next-step ticket; forged `workerId`; and changed operation/run/generation. These remain synthetic tests, not production authorization evidence.

### Independent stop authority after revocation

Revocation, lease loss and deadline are reasons to stop, not prerequisites for new execution. The host termination supervisor is a separate host-systemd service and accepts a stop request through `/run/omnis/terminator/stop.sock`, created below a root-owned non-writable directory, socket owned by `omnis-runtime-terminator`, mode `0660`, and a dedicated caller group containing only the Authorizer service UID. It authenticates exact `SO_PEERCRED` host UID/GID and an Authorizer-signed stop-only capability. A distinct stop-signing key is provisioned by root from the owner-approved trust root, readable only by Authorizer; Gateway, Launcher and terminator receive only the public verification key. Issuer/key custody remains a TCB and owner decision. The stop capability is bound to `run_id`, `execution_generation`, stop operation ID and absolute deadline, reason, issue/expiry and unique stop ID. It has no `create/start/inspect` scope and cannot be transformed into an execution ticket. Only Authorizer may issue an immediate revocation/lease-loss stop-only capability, using its separately provisioned stop-signing key. At operation admission Authorizer also provides the terminator a pre-signed, bounded stop lease tied to exact run/generation and absolute deadline; the terminator can enforce that deadline without Authorizer/Gateway availability.

The terminator runs as dedicated non-login `omnis-runtime-terminator` UID/GID, distinct from all other roles. Its executable, system unit, socket parent, policy, verifier key and registry writer are root-owned; the service can read policy/key and write only its append-only evidence area. The system manager starts it independently of Runtime Engine and Gateway, uses `Restart=no` or a separately reviewed bounded restart policy, fixed request/time bounds and startup admission fencing. It verifies the signed stop scope and matches it against a trusted registry entry populated only by a system-manager-owned registration mechanism. Launcher, Gateway and Docker labels/API responses cannot choose or replace the cgroup target. Unknown/mismatched cgroup identity fails closed without touching another run. Per-run cgroup creation, registration and process/helper coverage are **OPEN — DESIGN** because the rootless daemon's placement authority and independent mapping mechanism are not yet resolved. Whole-service bounded kill can be an explicit coarse fallback only if owner-approved; it must target the exact Runtime service cgroup and is not per-run proof.

Stop processing never asks Authorizer for an ordinary execution ticket. A previously issued stop-only capability or a root-provisioned, bounded deadline lease remains usable during Authorizer/Gateway outage; if neither exists, supervisor records a failed attempted stop and preserves unknown state. If no valid stop capability or registered mapping is available, the supervisor records `stop_attempted`, keeps the run `unknown/quarantined`, triggers the independently authorized whole-service/VM emergency procedure if one exists, and reports no confirmed termination. Durable attempted and confirmed evidence includes exact run/generation/stop ID, cgroup identity, manager invocation/result, monotonic time/boot epoch and observed empty cgroup/process/helper inventory; evidence storage failure cannot be represented as success. Timeout, supervisor restart, partial process survival or lost acknowledgement yields `unknown`, never `stopped`. Synthetic cases: revoke then stop succeeds without execution ticket; lease loss/deadline during Authorizer outage still invokes held stop lease; foreign run/generation/cgroup substitution denied; stop capability cannot create/start; Gateway unavailable; partial survivor and lost confirmation remain unknown.

## Durable journal and restart admission fence

Authorizer's transactional reservation ledger is one-use authority only within its own integrity and rollback domain; the Gateway-local append-only journal is additional evidence, not an independent anti-rollback anchor. Each record binds boot/instance epoch, monotonically increasing sequence, previous-record hash, `jti`, operation/step, request digest, authorization/lease revision, dispatch marker and response classification. Only one Gateway process may own a journal: systemd singleton plus exclusive `flock` held on a root-owned directory and a file lock; a second process must fail startup before binding UDS. Journal file is Gateway-writable only; directory, unit, binary and policy are provisioner-owned.

Before any Engine bytes, append the consumed/reserved record and dispatch-attempt marker, `fdatasync`/`fsync` the file, then `fsync` the containing directory for newly created/renamed records; only then issue the request. After response, append and sync the classified result. This ordering is a design requirement, not a claim that a particular filesystem, virtual disk cache, VHDX, or hypervisor honors power-loss durability. Feasibility evidence must record filesystem/mount/barrier/cache configuration and perform abrupt guest and externally controlled VM power-loss cases. Process-kill hooks alone do not prove power-loss durability.

Missing, corrupted, ambiguous, older-than-external-high-water, hash-chain-mismatched or snapshot-rolled-back journal closes admission. Multiple writer detection also closes admission. A VM snapshot may restore both Core PostgreSQL and the Gateway journal because both may share one guest rollback domain. Local comparison cannot detect a consistent rollback. No rollback prevention/detection is claimed until Option A below is implemented and independently verified. Under Option A, reopen requires an independent current anchor receipt plus intact signed binaries/policy, one Gateway writer, exact read-only Engine reconciliation, no surviving unowned process/cgroup and a current revocation/lease check. Under Option B, restoring or importing state always closes admission; only a separately owner-approved manual re-provisioning with a fresh environment identity, rotated authority and all prior operations quarantined may resume synthetic-only work. Unknown outcomes remain quarantined; no missing object authorizes replay.

### Rollback anchor choices and trust assumptions

**Option A — independent monotonic authority (preferred, not implemented):** an owner-selected anchor outside the entire guest/distro snapshot and export/import rollback domain (candidate custody: remote append-only service under a separately administered identity, or a hardware monotonic counter/TPM-backed service whose reset/restore semantics are independently evidenced). The anchor identity, signer, administrators, key custody, durability, backup/restore and incident process must be named and owner-approved. ## Controlling remediation contract — C-1, C-2, C-3, R-03 and M-4

### C-1: authoritative step outcomes

Authorizer owns a transactional step ledger keyed by `(environment_epoch, operation_id, step_index, reservation_id, reservation_revision, ticket_jti)`, binding authorization/task/profile/lease revisions, run/generation and exact request/payload digest and length. Only the authenticated Worker may request the next ticket; Launcher claims cannot advance the ledger. Gateway reports outcomes directly on a separate Authorizer-owned outcome UDS with root-owned non-writable parents, mode 0660, dedicated Gateway caller group and exact host SO_PEERCRED UID/GID. Outcome reports additionally carry an issuer-bound Gateway signature, pinned Gateway instance/boot epoch, unique report ID, expected ledger revision, ticket tuple, request digest, outcome class and bounded evidence digest. Root provisions the Gateway reporting key and Authorizer verifier registry; Launcher and workloads cannot read the private key. Custody and rotation require owner approval.

The serialized states are RESERVED → CONSUMED → DISPATCHED → ACKNOWLEDGED or UNKNOWN. Authorizer commits RESERVED on authenticated issuance. Before Engine bytes, Gateway syncs its local consumption/dispatch-intent journal, reports CONSUMED, and receives the Authorizer's durable consumption receipt. Gateway then reports DISPATCHED as **dispatch may occur**, receives its durable receipt, and only then attempts the exact Engine step once. DISPATCHED is not proof bytes reached Engine. Gateway records Engine acknowledgement locally and reports ACKNOWLEDGED with the exact reconstructed request and bounded response evidence; Authorizer records it only after authenticated tuple/revision validation. An Engine create acknowledgement is not runtime completion. Before issuing start, read-only evidence must establish the exact inert object's identity/configuration; final runtime completion needs independently correlated terminal evidence. Launcher cannot report or attest any outcome.

Identical report-ID/tuple/content replays return the original receipt without another transition. Conflicting content, stale revision, wrong Gateway identity/instance, skipped states or foreign ticket/run/generation fail closed. Authorizer increments the ledger revision transactionally and advances the expected step index only after a known result or accepted read-only reconciliation under current authorization and lease revisions. Concurrent reports serialize. UNKNOWN may be recorded by Gateway or by Authorizer's recovery timeout; neither permits another create/start for that step. Late acknowledgements are evidence for reconciliation, never an implicit step advance.

After any crash, missing consumption/dispatch receipt, lost Engine response, Authorizer outage or disagreement, admission stays fenced and the step is UNKNOWN unless durable records prove it never reached CONSUMED. Gateway may resend an identical **outcome report**, never the Engine mutation. Recovery compares Authorizer receipts, journal and anchor using read-only Engine inspection; missing objects do not authorize recreation. Outcome evidence is trusted only within the explicitly accepted Gateway/Engine TCB and is not independent proof against daemon compromise.

### C-2: stop capability binding without a pre-existing cgroup

At admission, a stop lease binds only `(environment_epoch, run_id, execution_generation, stop_operation_id, absolute_deadline, reason, issuer, audience, key_id, not_before, expires_at)`. It does not require or accept a caller-selected cgroup, PID, path or Docker ID. Immediate revocation/lease-loss stop intents use the same identity tuple and a unique stop operation ID. Distinct execution and stop signing keys/scopes remain mandatory. A stop intent cannot create/start or authorize a replacement run.

The independent terminator resolves the tuple through its trusted registry **after registration**, checks registration epoch/generation and a pinned kernel cgroup handle/identity, then applies bounded TERM/KILL and verifies all registered processes/helpers absent. Missing registration records stop intent durably, fences the run and triggers only a separately approved emergency scope; it never guesses a cgroup. Identical stops are idempotent; foreign generations, substituted registrations and stop-ID conflicts deny without touching another run. A held bounded stop lease permits deadline enforcement during Authorizer/Gateway outage. Immediate lease-loss detection requires authenticated Authorizer evidence or expiry of a previously registered bounded lease; outage is never proof of lease renewal. ### C-3: external anchor includes revocation and supersession

Option A must anchor both consumption and authority changes outside the complete guest rollback domain. A restored active authorization preceding an anchored revocation or lease supersession is rejected even if the restored local DB and journal agree. Missing history, wrong epoch, replayed challenge, anchor mismatch or ambiguous update closes admission and quarantines affected operations. Recovery never lowers anchor state or automatically selects a new epoch. An independent owner-controlled epoch reset/reprovisioning process must retire prior authority. Local journal durability does not provide this property. Option B remains explicit whole-environment rollback-risk acceptance, restricted to synthetic-only work with fresh identity/keys and quarantined prior operations. **M-3 remains BLOCKED — OWNER DECISION**; neither option nor any external service is selected.

### Independent review corrections: admission fence, actuator and stop validity

**Start-admission fence:** RESERVED/create authority never implies start authority. Before issuing a start ticket, Authorizer must possess an authenticated durable registration acknowledgement from the independent registrar/terminator for the exact environment/run/generation, registration revision and immutable stop scope. The acknowledgement binds the stop lease, actuator identity and pinned kernel target (or independently registered per-run VM identity). Gateway verifies that acknowledgement digest/revision in the start ticket. Missing, stale, replaced, revoked or unverified registration denies start with zero Engine bytes. A stop intent arriving before registration permanently fences that generation; later registration cannot silently clear it. Because the shared-daemon trusted registration mechanism remains unresolved, this fence currently prevents integrated per-run start; no temporary labels/API mapping may bypass it.

**Terminator actuator boundary:** the unprivileged terminator does not receive general systemd D-Bus, sudo, shell, arbitrary PID/path or Engine authority. A separately provisioned root-owned minimal actuator exposes one bounded AF_UNIX operation, `terminate_registered_scope`, accepting only exact terminator SO_PEERCRED and a registrar-issued opaque registration handle plus run/generation/registration revision/stop ID. The actuator independently validates the signed registration and stop scope, obtains the pinned kernel cgroup descriptor from its root-owned registry, verifies boot identity and liveness against reuse/substitution, and performs bounded signals/cgroup kill only within that registered scope. Callers cannot select a unit name/path or request arbitrary system-manager methods. For a VM candidate, an equivalently narrow independent hypervisor actuator resolves an opaque VM registration handle. Root provisioner owns actuator executable, unit, ACL and registry; registrar alone creates mappings. Actuator authority and kernel permissions must be explicitly approved, implemented and independently verified; this design grants no existing service those privileges. Shared-daemon registration/process coverage remains M-4 OPEN — DESIGN even with this proposed actuator API.

**Stop validity and clocks:** the prearmed stop lease must be accepted and durably armed before start admission, with `not_before <= admission_time`, absolute deadline bounded by the execution policy, and `expires_at >= absolute_deadline + maximum_termination_grace + evidence_window`; every quantity has a reviewed finite upper bound. Only authenticated owner-approved renewal of the same generation before expiry may change a lease, and never beyond the policy maximum; missing renewal does not extend execution. At arming, the terminator converts the validated absolute deadline into a boot-bound monotonic/boottime deadline using the reviewed clock policy. Wall-clock rollback, suspend semantics, boot change or expiry ambiguity fences new starts and triggers the preauthorized bounded stop/emergency procedure; an expired ticket must not cancel an already armed deadline obligation. If the actuator cannot validate authority or prove termination, record UNKNOWN and keep admission closed. Clock/TTL constants and emergency scope remain owner/security decisions, not inferred defaults.

Required Stage A negative fixtures: start before registration acknowledgement; wrong registration digest/revision/generation; registration after pre-registration stop; foreign actuator handle/peer; arbitrary unit/path request; stale boot/cgroup reuse; stop lease expiring before deadline/grace; wall-clock rollback/suspend/restart; lost renewal and actuator acknowledgement. ## N-2/N-3: authoritative cancellation and DB-to-anchor ordering

**Cancellation evidence:** owner cancellation persists an idempotent stop intent bound to environment/run/execution generation/stop operation. Authorizer authorizes the independent stop path; terminator resolves the trusted registration and actuator performs bounded termination. Only the terminator's authenticated attestation backed by actuator/kernel evidence for that exact tuple, including complete process/helper absence, can establish `cancelled`. Gateway and Docker daemon observations are advisory only. Docker stop/kill success, container removal, timeout or a Gateway report cannot establish cancellation. Missing acknowledgement, surviving process, incomplete inventory, stale generation or failed evidence persistence leaves UNKNOWN and admission fenced. Gateway outage cannot disable a previously armed independent deadline.

**Revocation writer and transaction:** Core/API receives owner intent only after owner-session and CSRF validation, with an idempotency key. It must forward a narrow authenticated revocation request to Authorizer; it cannot directly set authoritative authorization/lease revisions. No Core-container-to-host channel is selected: the proposed Authorizer-owned `/run/omnis/authorizer/revocations.sock` is not mounted into Core, and container UID translation is not a service identity. Until the owner selects and reviews a Docker-only-compatible channel, owner revoke/cancel requests cannot reach Authorizer and the real-runtime path stays disabled. Any future socket must be mode 0660 under root-owned parents, with an exact authenticated API identity plus a purpose-bound request; peer/group, transport, and credential custody are owner decisions. If the caller cannot be authenticated, deny. Lease supersession intent comes from the authenticated Worker/lease authority on its separate existing intent boundary. Authorizer alone commits each authoritative transition using its restricted DB role; API/Worker/Launcher/Gateway cannot bypass it. This is a future contract, not a claim about current mock-path ACLs.

Before contacting the external anchor, Authorizer first persists an idempotent `REVOCATION_REQUESTED` or `LEASE_SUPERSESSION_REQUESTED` fence in its durable ledger, bound to the owner/lease intent, authority identity, expected revision and request key. This request fence immediately denies new ticket reservations and consumption for the affected authority; it is not yet an authoritative revocation and must be displayed as **pending, not yet protected**. It cannot be cleared by timeout, restart, or an automatic retry. Recovery resumes the same request and keeps execution fenced until the matching anchor pre-fence and authoritative DB transition complete, or an explicit owner recovery decision safely resolves it.

Before the authoritative transaction may commit revocation/supersession, Authorizer must obtain an independent anchor pre-fence receipt for the idempotent intent, authority/lease identity, expected old revision, proposed new revision and environment epoch. The anchor serializes this pre-fence against ticket consumption. If the pre-fence wins, it denies new `RESERVED` issuance and consumption of every still-`RESERVED` ticket for the old revision; a matching `CONSUMED` receipt committed first remains valid for that exact step only. The pre-fence is irreversible except by a separately approved new authority identity. The DB transaction validates and stores that receipt. If anchor pre-fencing fails or times out, authoritative commit is deferred, the durable request fence remains, new execution stays denied, and owner stop intent/held stop leases still apply. An owner-visible outcome remains pending, not yet protected; timeout does not resume execution. A DB rollback or loss after successful pre-fence cannot erase the external denial. The Authorizer transaction serializes with reservations on the same authority/lease identity, increments its revision, sets the revocation/supersession tombstone, fences new reservations, and inserts an immutable idempotency receipt plus durable anchor-outbox record atomically. **The DB commit immediately denies new authority**, even before anchor confirmation. A `RESERVED` ticket without a prior matching `CONSUMED` receipt is not grandfathered; a step consumed before the pre-fence may dispatch once, while subsequent tickets deny. Lease supersession retires the prior lease revision; replacement authority cannot start while anchor state is pending or uncertain.

States: `ACTIVE → REVOCATION_REQUESTED → PREFENCED_DB_PENDING → REVOKED_ANCHOR_PENDING → REVOKED_ANCHORED` (equivalently `LEASE_CURRENT → LEASE_SUPERSESSION_REQUESTED → LEASE_PREFENCED_DB_PENDING → SUPERSEDED_ANCHOR_PENDING → SUPERSEDED_ANCHORED`). No timeout, restart or automatic retry reverses a request fence. The outbox dispatcher is Authorizer-authenticated and advances Option A's independent anchor using the immutable DB transition identity, old/new revisions, tombstone and environment epoch. Anchor receipt must match the exact transition and be persisted transactionally before returning **durably rollback-protected**. The API reports `pending, not yet protected` while only the request fence or pre-fence exists, and may report `effective, protection_pending/unknown` only after DB commit; it never reports durable protection before receipt. Anchor failure does not undo the request fence or enable reservations. Anchor outage fences all new execution; held stop leases remain armed. Any restore starts quarantined until the restored request ledger, protected restore manifest and external anchor history reconcile; an `ACTIVE` row alone never proves there was no pending request.

If DB commit acknowledgement is lost, retry the original idempotency key by durable lookup; do not create a new transition or assume ACTIVE. If anchor response is lost, query/retry the same compare-and-advance identity; no revision lowering or second semantic transition. If anchor succeeded but receipt persistence failed, recover the original signed receipt and retain the DB fence meanwhile. Boot/reconnect/snapshot restore requires a fresh independent anchor challenge and exact authority high-water comparison before any reservations. A restored DB predating anchored revocation is rejected. A restore that omits or conflicts with a locally pending request fence is quarantined and cannot resume from an `ACTIVE` row; it requires external intent reconciliation and explicit owner resolution. For the DB-committed but not yet finalized window, the independently persisted pre-fence continues to deny the old revision even after guest rollback. The anchor finalizes that same intent only after the committed DB transition is submitted; finalization loss never removes its pre-fence. If pre-fence succeeded but DB commit failed, Authorizer recovers the immutable external intent and completes the same transition; it cannot cancel the fence or resume old authority. Fresh online anchor admission checks are mandatory for every issuance/consumption, not just boot, and reject an unresolved pre-fence before accepting restored DB state. No local session/epoch marker substitutes for this independent check. Unknown/missing pre-fence history, replayed admission receipts or inability to bind each receipt to a fresh request and exact revisions denies execution. This is the required rollback-independent mechanism for Option A, not an implemented or selected service; an anchor incapable of these semantics is unsuitable. M-3 stays **BLOCKED — OWNER DECISION**.
