No document may call the Gateway independent of the daemon while packaging it under that daemon.

## Worker identity and trusted intent

Authorizer authenticates the Worker at the Worker→Authorizer UDS using `SO_PEERCRED` exact host UID/GID plus the protected socket path. `workerId` is a database lease label and request metadata only; it is never identity evidence. Authorizer binds authenticated service identity to the authoritative `(task_id, project_id, run_id, generation, lease_owner, lease_expiry, task_revision, authorization_revision)` read from its restricted DB role. Worker cannot assert or override lease ownership. It must prove current lease ownership by matching DB state; generation is a fencing token. Each intent carries unique request nonce and operation ID, and Authorizer rejects duplicate, expired, revoked, superseded, wrong-task, wrong-project, wrong-run or wrong-generation intents. Replay state is durable and unique by issuer, nonce, operation and step.

The trust base includes host root/systemd, kernel peer credentials, immutable Worker executable/config and the DB lease authority. The Core Engine cannot impersonate `omnis-worker`: its subordinate ranges exclude the service UID and it has no Worker socket mount. A compromised Worker can request work only under its own active lease and owner grant; it remains trusted to form task intent. If peer credentials, socket ownership, DB lease state, task binding, nonce store, or trusted clock is unavailable or inconsistent, Authorizer denies issuance and Gateway denies dispatch. Synthetic negative fixtures must spoof `workerId`, connect from launcher/Core/runtime UIDs, replace socket paths, pass inherited FDs, replay nonce, and mix task/run/generation/lease values; all must yield zero Engine dispatch.

## Versioned per-step authorization and input contract — design only

Version 1 proposals in the P0-R2.2 plan are superseded where they omit the fields and state transitions below. This is a future contract only; production protocol code is unchanged. One immutable operation has a canonical `operation_id`; `step_index` starts at 0 for `create` and increases by exactly one for each following ticketed step, including read-only `inspect`, `read_output` and `reconcile`; the Authorizer maintains the authoritative expected next index and rejects skips/reordering. Each has an exact `step_type` (`create`, `start`, `inspect`, `read_output`, or `reconcile`). Mutation steps `create` and `start` each require a separate one-use ticket. Read-only `inspect`/`read_output`/`reconcile` use distinct one-use read tickets and can never mutate or recreate. `cancel` is not an ordinary operation ticket or Gateway operation; a separate stop-socket response is bound to the exact run/generation and stop ID. The proposed maximum execution-ticket lifetime is 30 seconds, subject to Codex #1 approval; clock uncertainty rejects.

Each signed ticket binds: `protocol_version`; `operation_id`; `step_index`; `step_type`; `reservation_id` and monotonic `reservation_revision`; `authorization_id` and `authorization_revision`; `task_id`/`task_revision`; `profile_id`/`profile_revision`; `project_id`; `run_id`; `execution_generation`; `lease_id`, `lease_owner` and `lease_revision`; exact `input_profile_version`, `input_digest` and `input_length` (zero/null only for operations that do not consume input); policy digest/restrictions; `iss`, `aud`, and peer subject derived from kernel credentials; `jti` one-use ticket ID; `not_before`; `expires_at`; and a bounded operation request digest. IDs/revisions are typed, canonical and non-path values. A ticket is valid only for the exact next expected step, tuple and payload, at the exact policy and lease revisions. A one-step ticket cannot authorize another step, another payload, retry dispatch, or another peer. TTL has a fixed reviewed upper ceiling; clock uncertainty, expiry boundary ambiguity, unknown key or unavailable revocation/lease state denies before consume. Exact numeric TTL and clock rules remain an implementation/security decision.

### Worker → Authorizer → Launcher → Gateway flow

1. Worker obtains task/profile/run/generation and lease evidence from its authenticated service context; it does not accept caller `workerId` as authentication. Worker connects directly to Authorizer over the protected UDS. Authorizer checks exact host `SO_PEERCRED`, current owner authorization, task/profile revisions, active lease owner/revision/expiry, generation, operation ordering and unique Worker intent nonce against authoritative state.
2. Worker submits the exact immutable payload bytes (or an authenticated immutable object reference whose fetched bytes are re-hashed) to Authorizer with task/profile/run/generation. Authorizer obtains or verifies the authoritative payload itself; a digest supplied only by Worker/Launcher is insufficient. It enforces the 65,536-byte maximum and computes the domain-separated payload digest over exact bytes plus payload profile version, revisions, run and generation.
3. Worker requests the initial ticket for the next step from Authorizer. Authorizer authenticates Worker by exact host peer UID/GID, serializes the request with revocation and lease changes, commits a unique reservation row, then signs the ticket. Authorizer returns that signed ticket and reservation receipt to the authenticated Worker; Worker forwards them to Launcher over the Worker→Launcher UDS, whose receiver independently checks exact host peer UID/GID. The Launcher does not become an issuer or ticket requester; launcher-supplied `workerId` remains metadata only.
4. Launcher is the caller that transports the ticket and opaque input bytes to Gateway. Launcher cannot request or mint the next ticket. After a step reaches a known terminal/reconciled state, the authenticated Worker requests the next ticket directly from Authorizer using the same operation ID plus next step index and a fresh intent nonce. Authorizer checks prior-step state, same task/profile/input tuple, current lease/revisions and authorization. This prevents Launcher-controlled step advancement.
5. Gateway verifies Launcher `SO_PEERCRED`, issuer/key/audience, subject, all revisions, expected step index/type, operation/request digest, expiry, restrictions and exact input length/digest. It durably consumes the ticket before any Engine request byte. For `create`, Gateway stages exactly the verified bytes read-only and reconstructs a fixed image/command request. `start` is a separate reservation after `create` is reconciled as the exact inert object. `inspect` and `reconcile` are read-only and never imply absence is permission to recreate. Each read query has bounded output, fresh request/ticket identity and no raw daemon identifiers. Unknown or mismatched state stays quarantined.

Authorizer reservation state is `ISSUED/RESERVED → CONSUMED` with a unique constraint over issuer plus `jti`, operation and step, and a serialized expected-step revision. A competing consume/reservation loses and returns `REPLAY_CONFLICT`; it cannot dispatch. The gateway journal transition is `ticket_verified → consume_fsynced → dispatch_attempted → known_result | unknown`. Durable consume precedes writing Engine bytes. A crash after consume and before/within dispatch is `unknown`; never reissue that step or infer “not executed” from a missing object. Reconciliation is read-only and independent termination is used if the effect cannot be bounded.

The revocation and lease linearization rule is the Authorizer transaction: revocation/lease supersession committed before reservation denies the ticket; a reservation committed first authorizes only that exact step and may proceed despite a subsequent revocation. Revocation after consume but before dispatch does not roll back the one reserved step; it marks the authorization revoked, prevents subsequent tickets and raises a stop request. A create that commits before a start ticket is denied remains inert and must be stopped/quarantined. No atomicity across DB and Engine is claimed. Gateway/Authorizer restart starts fenced; status, DB, signature, clock, journal or anchor uncertainty denies new tickets.

Negative Stage A fixtures must prove zero dispatch for: one-byte, whitespace, Unicode and cross-run payload substitution; mismatched digest/length or unavailable reference; stale authorization/task/profile/lease/reservation revision; wrong step index/type/order; expired/future/clock-uncertain ticket; wrong peer/audience/issuer/key; duplicate ticket; concurrent duplicate consumption; launcher attempt to request a next-step ticket; forged `workerId`; and changed operation/run/generation. These remain synthetic tests, not production authorization evidence.

### Independent stop authority after revocation

Revocation, lease loss and deadline are reasons to stop, not prerequisites for new execution. The host termination supervisor is a separate host-systemd service and accepts a stop request through `/run/omnis/terminator/stop.sock`, created below a root-owned non-writable directory, socket owned by `omnis-runtime-terminator`, mode `0660`, and a dedicated caller group containing only the Authorizer service UID. It authenticates exact `SO_PEERCRED` host UID/GID and an Authorizer-signed stop-only capability. A distinct stop-signing key is provisioned by root from the owner-approved trust root, readable only by Authorizer; Gateway, Launcher and terminator receive only the public verification key. Issuer/key custody remains a TCB and owner decision. The stop capability is bound to `run_id`, `execution_generation`, registered cgroup identity/inode, reason, issue/expiry and unique stop ID. It has no `create/start/inspect` scope and cannot be transformed into an execution ticket. Only Authorizer may issue an immediate revocation/lease-loss stop-only capability, using its separately provisioned stop-signing key. At operation admission Authorizer also provides the terminator a pre-signed, bounded stop lease tied to exact run/generation/cgroup and absolute deadline; the terminator can enforce that deadline without Authorizer/Gateway availability.

The terminator runs as dedicated non-login `omnis-runtime-terminator` UID/GID, distinct from all other roles. Its executable, system unit, socket parent, policy, verifier key and registry writer are root-owned; the service can read policy/key and write only its append-only evidence area. The system manager starts it independently of Runtime Engine and Gateway, uses `Restart=no` or a separately reviewed bounded restart policy, fixed request/time bounds and startup admission fencing. It verifies the signed stop scope and matches it against a trusted registry entry populated only by a system-manager-owned registration mechanism. Launcher, Gateway and Docker labels/API responses cannot choose or replace the cgroup target. Unknown/mismatched cgroup identity fails closed without touching another run. Per-run cgroup creation, registration and process/helper coverage are **OPEN — DESIGN** because the rootless daemon's placement authority and independent mapping mechanism are not yet resolved. Whole-service bounded kill can be an explicit coarse fallback only if owner-approved; it must target the exact Runtime service cgroup and is not per-run proof.

Stop processing never asks Authorizer for an ordinary execution ticket. A previously issued stop-only capability or a root-provisioned, bounded deadline lease remains usable during Authorizer/Gateway outage; if neither exists, supervisor records a failed attempted stop and preserves unknown state. If no valid stop capability or registered mapping is available, the supervisor records `stop_attempted`, keeps the run `unknown/quarantined`, triggers the independently authorized whole-service/VM emergency procedure if one exists, and reports no confirmed termination. Durable attempted and confirmed evidence includes exact run/generation/stop ID, cgroup identity, manager invocation/result, monotonic time/boot epoch and observed empty cgroup/process/helper inventory; evidence storage failure cannot be represented as success. Timeout, supervisor restart, partial process survival or lost acknowledgement yields `unknown`, never `stopped`. Synthetic cases: revoke then stop succeeds without execution ticket; lease loss/deadline during Authorizer outage still invokes held stop lease; foreign run/generation/cgroup substitution denied; stop capability cannot create/start; Gateway unavailable; partial survivor and lost confirmation remain unknown.

## Durable journal and restart admission fence

Authorizer's transactional reservation ledger is one-use authority only within its own integrity and rollback domain; the Gateway-local append-only journal is additional evidence, not an independent anti-rollback anchor. Each record binds boot/instance epoch, monotonically increasing sequence, previous-record hash, `jti`, operation/step, request digest, authorization/lease revision, dispatch marker and response classification. Only one Gateway process may own a journal: systemd singleton plus exclusive `flock` held on a root-owned directory and a file lock; a second process must fail startup before binding UDS. Journal file is Gateway-writable only; directory, unit, binary and policy are provisioner-owned.

Before any Engine bytes, append the consumed/reserved record and dispatch-attempt marker, `fdatasync`/`fsync` the file, then `fsync` the containing directory for newly created/renamed records; only then issue the request. After response, append and sync the classified result. This ordering is a design requirement, not a claim that a particular filesystem, virtual disk cache, VHDX, or hypervisor honors power-loss durability. Feasibility evidence must record filesystem/mount/barrier/cache configuration and perform abrupt guest and externally controlled VM power-loss cases. Process-kill hooks alone do not prove power-loss durability.

Missing, corrupted, ambiguous, older-than-external-high-water, hash-chain-mismatched or snapshot-rolled-back journal closes admission. Multiple writer detection also closes admission. A VM snapshot may restore both Core PostgreSQL and the Gateway journal because both may share one guest rollback domain. Local comparison cannot detect a consistent rollback. No rollback prevention/detection is claimed until Option A below is implemented and independently verified. Under Option A, reopen requires an independent current anchor receipt plus intact signed binaries/policy, one Gateway writer, exact read-only Engine reconciliation, no surviving unowned process/cgroup and a current revocation/lease check. Under Option B, restoring or importing state always closes admission; only a separately owner-approved manual re-provisioning with a fresh environment identity, rotated authority and all prior operations quarantined may resume synthetic-only work. Unknown outcomes remain quarantined; no missing object authorizes replay.

### Rollback anchor choices and trust assumptions

**Option A — independent monotonic authority (preferred, not implemented):** an owner-selected anchor outside the entire guest/distro snapshot and export/import rollback domain (candidate custody: remote append-only service under a separately administered identity, or a hardware monotonic counter/TPM-backed service whose reset/restore semantics are independently evidenced). The anchor identity, signer, administrators, key custody, durability, backup/restore and incident process must be named and owner-approved. After the Authorizer reservation transaction and Gateway local journal sync, Gateway performs an idempotent compare-and-advance tuple `(environment_id, epoch, sequence, previous_digest, consumed_ticket_id)`; it may dispatch only after the anchor authenticates the caller, rejects reused/lower sequence or conflicting digest, atomically advances once, and returns a signed receipt for the exact tuple. Admission requires a fresh challenge/receipt bound to the current epoch plus exact DB/journal high-water. Network, anchor, signature, clock, or receipt uncertainty fails closed; snapshot restore cannot reopen admission until an independently authorized fresh epoch is established and all stale runs are quarantined. This is a proposed protocol, not proof that a selected remote/HSM/TPM service provides these semantics.

**Option B — explicitly accepted whole-environment rollback risk:** owner may decide that rollback of the entire Core DB/Authorizer ledger and Gateway journal is outside the threat model. This loses detection of replayed consumed tickets and may also restore revoked authorization/lease state; a restored guest can repeat an effect unless every affected operation is treated unknown. It would require no automated snapshot/import/restore while runtime authority exists, no live or persistent provider credentials, synthetic-only operations, manual owner fence and fresh environment identity after restore, all prior operations quarantined, and re-provisioned keys/epoch before any new admission. This is not equivalent to rollback prevention. It requires a separate explicit owner risk decision and independent security acceptance; absent that decision, fail closed.

**Trust assumption:** Core PostgreSQL administrator and the DB owner/superuser can alter the authorization ledger, task/authorization revisions and revocation state. The Authorizer's DB role, grants, migrations, constraints, backups and restore authority are part of the TCB. Gateway cannot prove ledger integrity against the Core DB administrator unless Option A supplies independent monotonic evidence. Anchor custody is **BLOCKED — OWNER DECISION**; neither option is selected. Missing, rolled-back, corrupt or ambiguous journal/ledger state closes admission and preserves unknown outcomes.

## Egress and termination enforcement candidates

Egress is not enforced by Runtime Engine configuration alone. Candidates to test independently are a host-owned network namespace and nftables policy around the daemon and all RootlessKit/slirp4netns/pasta helpers; systemd cgroup-v2/BPF restrictions where the selected kernel/systemd actually supports them; and a no-uplink private VM network with hypervisor firewall as an outer boundary. Each must be measured for IPv4, IPv6, DNS, loopback, AF_UNIX, AF_VSOCK/Hyper-V sockets where exposed, Windows interop, automount, D-Bus/varlink and every accessible daemon socket. Record kernel features, nftables hooks/priority/counters, cgroup-BPF attachment, namespace/process/FD inventory and the exact enforcing point. A missing route or unreachable sink is inconclusive. Same-path positive, denied, restored-positive controls are required; no public endpoint is used.

Termination authority must be outside Worker, Launcher, Gateway and Runtime Engine: a root-owned system manager plus separately provisioned terminator controls an exact Runtime service/run cgroup, fixed deadline and startup fence. `RuntimeMaxSec`/`KillMode=control-group` bound the whole Runtime daemon/helper/container service tree only; Gateway is a separate service and must not be included in that cgroup test. They are not per-run termination. Prove dockerd, RootlessKit, containerd/shim, container process and helper descendants occupy the intended unit/cgroup and that cgroup kill reaches each while Gateway and daemon APIs are unavailable. Restart is `no`; startup stays fenced until stale state reconciles; exact resource ownership is required for cleanup. Hypervisor destruction is sufficient only as final destruction of the disposable VM and disk after in-guest evidence collection. It is not proof of bounded per-run termination or a PASS for active-workload termination.

## Corrected candidate trust architecture — design only

The following closes the review ambiguity in the design. It specifies a candidate to review; it does not create or authorize services.

### Gateway provisioning and identity

- The Runtime API Policy Gateway is a **host system service**, never a container controlled by either Docker Engine. Root/systemd is a trusted host-provisioning authority only if the owner explicitly accepts host root and the signing/update chain in the trust base.
- Proposed service identity: dedicated non-login `omnis-runtime-gateway` UID/GID, distinct from the `omnis-runtime-engine` and `omnis-launcher` host identities and outside both engines' subordinate UID/GID ranges. The Gateway has no database credential, no shell, no provider credential, no host-home access and no Engine-admin group.
- A root-managed Runtime Engine system unit runs rootless as `omnis-runtime-engine` with `Delegate=yes`. The proposed path is `/run/omnis/runtime-engine/docker.sock`: `/run/omnis` is root-owned/non-writable; its `runtime-engine` child is owned by the dedicated Engine UID, traversable by the Gateway group, and not accessible to launcher/Core identities; the socket is Engine-owned, mode `0660`, with a Gateway-only client group. Only the Gateway is an authorized **client**; the Engine daemon itself necessarily owns the listener and has full authority over its Engine. It is a trusted computing base component, and Gateway policy does not constrain a compromised daemon. If the owner requires containment of a compromised daemon, this architecture is blocked and needs a stronger isolation boundary such as a separately disposable VM. The socket is not mounted into any container.
- Proposed launcher→Gateway UDS: root-created non-writable parent directory, exact launcher-only group traversal, socket owned by Gateway and that group, mode `0660`. `SO_PEERCRED` must match the single dedicated host launcher UID. The launcher receives only this typed UDS, never a Runtime Engine socket, alternate context, TCP endpoint, inherited descriptor or gateway update control.
- Core Engine UID maps must not map a container identity to the launcher UID. Otherwise Core Engine authority can impersonate the UDS peer and this identity boundary is **BLOCKED**. Container identity/name is not peer authentication.
- The Engine-owned socket directory means a compromised Engine UID can replace its own socket path; this is within the explicitly trusted Runtime Engine TCB. No launcher/Core/Runtime-workload UID may write or replace any Gateway-facing path. Tests must inspect every path component, owner/mode/inode and symlink behavior and attempt substitution as each untrusted identity; the Runtime Engine UID result is reported as the stated trust assumption, not a gateway containment pass.
- Binary, systemd unit, trust anchors, policy and daemon configuration are root-owned and non-writable by Gateway, launcher and either Engine. The Gateway reads a signed/pinned policy/config digest from a root-owned directory; the small journal is in a separate Gateway-writable, launcher-inaccessible state directory. Policy updates use an owner-approved, signature-verified package and an atomic integrity check. Only the trusted host provisioner/root system manager may install, rollback or restart it. There is no Docker-driven update path or self-update.
- Candidate unit hardening includes `NoNewPrivileges=yes`, empty ambient/capability sets, `ProtectSystem=strict`, `ProtectHome=yes`, private tmp/devices, restricted syscalls, `RestrictAddressFamilies=AF_UNIX`, and `IPAddressDeny=any`. Whether each setting is supported and effective on the selected Linux/WSL build must be inspected and tested; listing it is not enforcement evidence. The Gateway parser should be memory-safe and treat daemon/workload output as bounded opaque bytes.

### Independent termination and recovery

The candidate Runtime Engine is supervised by the **system** systemd manager, not its `systemd --user` instance: root-owned unit, `User=omnis-runtime-engine`, `Delegate=yes`, explicit CPU/memory/task bounds, `RuntimeMaxSec`, `KillMode=control-group`, `Restart=no`, and live-restore disabled. A separately reviewed host terminator is required for per-run cancellation; it accepts only a signed stop-only `(run_id, execution_generation, stop_id, reason, expires_at)` on the dedicated UDS, maps it to an exact system-manager registered cgroup identity, sends TERM then bounded KILL, and verifies container, shim and helper process/cgroup absence. The secure registration/mapping is OPEN — DESIGN; do not claim per-run authority or evidence until that gap is resolved. It exposes no shell, arbitrary PID/path, Docker API or wildcard cleanup. Exact owner-labelled resource manifests prevent cross-run removal.

System-manager ownership and a future terminator are not implemented. Hypervisor-controlled destruction of the exact named no-uplink disposable Linux VM is an independent final environment terminator for VM-stage cleanup and may recover from a failed test. It does **not** prove in-guest/per-run kill behavior or that container removal killed escaped helpers; those tests need system-manager/cgroup evidence before the VM is destroyed. WSL distro termination is not a substitute for a tested in-guest terminator. Missing manager, journal, boot-ID fence or exact ownership keeps admission closed and state quarantined. No broad prune or automatic restart/replay.
