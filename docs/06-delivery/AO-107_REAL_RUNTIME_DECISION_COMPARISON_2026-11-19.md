# AO-107 Real-Runtime Provider Decision Comparison

**Status:** Decision package; no real provider is enabled.  
**Prepared:** 2026-11-19  
**Scope:** Provider authentication and first bounded read-only model operation under the existing local WSL2/Docker-only Phase 1 design.

## Decision requested

Choose whether Omnis OS will remain a **personal project operated locally by its owner** for SIWC plan usage, or pursue a different eligibility path. OpenAI's published cookbook lists personal locally run projects separately from open-source projects. A repository license decision is therefore not required for the personal/local path. This is not approval to implement OAuth, register a client, access credentials, activate a provider, make a provider request, or run on the target host.

The personal/local path is the strongest fit for the current single-owner local product description. Its applicability to the actual WSL2 installation remains conditional: OpenAI requires the local runtime to be controlled by the user and persistent tokens to stay local and under that user's control, not in a remote or managed environment. The device's management status, user control, selected account/workspace, plan eligibility, and exact task consent are unverified. Keep the runtime disabled until those are answered and Codex #3 independently accepts the host boundary.

## Existing Omnis OS controls and gaps

The current backend has synthetic fixtures for immutable task/profile/prompt binding, a fixed synthetic connector identity/version/operation, an empty tool/capability set, bounded limits, one-use grant consumption, expiry/revocation, and preservation of unknown outcomes. Those fixtures verify backend behavior; they do not establish host-enforced production controls or provider evidence. Ordinary Runs remain `runtimeKind: "mock"`, `synthetic: true`, and unknown for token/cost usage.

The current runtime authorization and host-boundary documents identify missing production controls: durable real-operation authorization fencing, credential brokerage and revocation, trusted connector process identity, effective cancellation evidence, network egress enforcement, and independently verified containment. Docker daemon access remains host-equivalent authority. This memo does not change those controls or the platform-owned documents.

### Runtime and consent fit

- OpenAI's `ext_agent_host_id` identifies a host for usage attribution but is not an authentication credential; even a public-key-derived ID is not proof of private-key possession. Codex #3 must provide separate authenticated host/process identity and continuity evidence.
- Omnis' current API, Worker, Authorizer, and synthetic broker arrangements are local, but the authorization architecture says processes share the Unix identity and the Worker has root-equivalent Docker authority. No SIWC token store or credential broker exists. A future token store must be local, user-controlled, and inaccessible to API, Worker, tool containers, logs, and artifacts.
- A company-managed Windows device is not automatically disqualifying, but it does not prove that token storage is “under the user's control” or outside a “managed environment.” The owner must confirm device ownership/management and applicable employer policy; if controls can access or centrally back up the credential store, do not use SIWC there without clarification from OpenAI.
- OpenAI's open-source cookbook names eligible ChatGPT Plus and Pro plans for the personal/local flow. Business workspaces have administrator permission and usage-sharing controls; do not infer eligibility from a successful identity sign-in. Confirm the actual account, selected workspace, enabled plan scope, and usage limits in OpenAI's UI. Existing Codex CLI login is not SIWC consent.
- One owner-started request can be bounded to the authenticated owner and connected Omnis app. Because processing continues in a queued Worker, the run UI must obtain explicit consent for that specific background operation before dispatch. Scheduled, recurring, or another person's triggered work remains disabled absent separate express consent. No sharing, pooling, resale, or general-purpose token/API access is permitted.

## Recommended first-operation shape (proposal, not implemented)

If the owner chooses SIWC, the first real operation should be a single direct Responses API request from one dedicated credential-broker/connector process. For this first operation, the broker and connector are the same process: it completes the narrowly scoped provider call internally and never returns or hands a token to a separate connector. Do not place the OAuth token in API or Worker memory, process arguments, an environment inherited by an agent/tool runtime, task workspace, database, event, log, or artifact. The broker/connector must not expose a general-purpose token proxy.

The grant and audit record should bind, at minimum:

- Owner identity, affirmative consent record, and consent timestamp.
- Immutable task ID/version, profile ID/version, exact prompt digest, input digest, and requested output boundary.
- Connector ID/version, provider, account/client registration identity, model, endpoint, and exact permitted operation.
- Unique authorization ID, operation/submission ID, audience, policy version, short expiry, revocation generation, resource limits, and a durable one-use consume-before-network-call state transition.
- `tools: []`, no MCP, shell, browser, file-system, child-agent, or other tool capabilities; request schema rejects unknown tool fields.
- Hard duration/output limits, one active operation, one provider request, and host-enforced provider-only egress.
- Provider stream/event identifiers, terminal status, and only provider-sourced usage fields with explicit provenance.

A local stop click or closed HTTP stream is only a cancellation request. Until the provider documents and returns authoritative interruption evidence, mark an interrupted submission `unknown`, preserve its original operation ID and audit, and never automatically resubmit. Recovery may read back only that same provider operation if the provider provides an authenticated lookup; otherwise owner reconciliation is required.

## Decisions and blockers

### Owner decisions

1. Confirm whether the intended use is strictly a personal, single-owner, local Omnis OS project on a user-controlled environment. Confirm whether the Windows/WSL2 installation is company-managed and whether policy and technical controls still permit local SIWC token storage under the user's control. Company management alone is not established as disqualifying, but it also does not establish user control; if the owner cannot confirm the Terms are met, pause this path and ask OpenAI for applicability guidance.
2. Confirm the selected ChatGPT account/workspace has an eligible plan and plan-use permission. Business workspace usage requires administrator allowance. Separately consent to Omnis OS and the ChatGPT Plan scope through OpenAI's authorization UI; no CLI credentials may be reused.
3. Approve exact read-only task, prompt, profile, model, maximum input/output, maximum duration, one-request concurrency, and any shared-plan usage/billing impact.
4. Decide whether to pursue the separate open-source route (including an explicit license choice), OpenAI's interest process for a paid/remote offering, or separately billed provider use. A repo license is needed only if choosing open-source distribution, not for personal-local use. None of these app categories or selections waives the SIWC Terms' user-control, local token-custody, authenticated-user, or consent requirements; if this host cannot meet them, SIWC is unavailable on this host.
5. Approve a local credential-custody/revocation policy and identify the dedicated secret-broker owner. This does not authorize live OAuth or provider calls by itself.
6. After independent platform acceptance, issue a separate exact-scope authorization for one real read-only run. No standing authorization is implied.

### Codex #3 platform dependencies

- Name the trusted connector and credential-broker processes, identities, lifecycle, and authenticated local IPC contract.
- Prove API/Worker cannot access the Docker socket, provider token, broker secret store, or provider endpoint.
- Prove only the fixed connector can reach named authentication/API endpoints, with DNS/IP/TLS behavior and redirect policy defined.
- Prove hard time, output, memory/CPU, and concurrency limits; admission fencing; revocation propagation; and independent process/descendant termination evidence.
- Define durable authorization journaling/anti-rollback and recovery after service, database, or host restart.
- Provide accepted target WSL2/Docker evidence under the separately approved platform procedure. This memo modifies no platform-owned documents.

### Provider questions still unverified

- Whether the actual WSL2/Windows host is user-controlled and not a managed environment for persistent SIWC token storage.
- Whether the owner's actual ChatGPT account/workspace and plan can use the ChatGPT Plan scope with a personal-local project.
- Whether the single-owner queued Worker execution is treated as background use requiring additional consent beyond a per-run explicit confirmation; terms require express consent before background use.
- Whether SIWC currently accepts this specific app/client and operation; public docs describe categories but do not certify Omnis OS.
- Exact credential custody allowed for this local WSL2 product and whether the selected storage mechanism meets OpenAI's published expectations.
- Whether SIWC's direct Responses API provides a provider-confirmed cancellation or same-operation readback primitive suitable for recovery.
- Which final response fields constitute authoritative per-run usage for this route and how plan-credit/limit outcomes are represented.
- Whether the app's read-only task and data handling meet current provider terms and plan/workspace controls.

## Recommendation

SIWC personal/local use is the recommended eligibility path to investigate, and a repository license is **not** a prerequisite for that category. It is not ready for implementation until the owner confirms the machine/runtime is user-controlled and the token store meets the Terms, account/workspace plan eligibility, per-run background consent, and the platform credential boundary. If user control or credential custody cannot be established, changing the app category, adding a license, or receiving private-app selection does not resolve that blocker; stop SIWC on this host pending OpenAI clarification. The paid/remote interest process is relevant to app eligibility only and does not waive these Terms. Separately billed provider credentials remain a distinct owner decision and authorization path. No live integration is enabled.
