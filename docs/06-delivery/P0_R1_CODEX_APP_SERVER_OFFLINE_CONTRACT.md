# P0-R1 Codex App-Server Offline Contract and Feasibility

**Status:** Design and synthetic fixtures only; provider execution remains blocked.
**Source baseline:** `fd576d19ad9f393970783533096da910a73bc8ef` (main after PR #111).
**Assessment date:** 2026-11-13.

## Executive assessment

Codex app-server is a technically plausible text-streaming protocol candidate: its documented flow initializes a client, starts or resumes a thread, starts a turn, streams item notifications, and reports a terminal turn status. It also documents interruption of a specific thread/turn.

**A strictly tool-free operation is not established. Real-provider integration is BLOCKED.** App-server exposes command, file, MCP, dynamic-tool, collaboration, browser/search, permission, and other tool/control surfaces. A text-only prompt and an application-side rejection of tool events do not prove that no action can occur before the event reaches the application. No documented app-server switch was found that is a complete, enforceable deny-all-tools guarantee. A host-enforced no-process/no-filesystem/no-network boundary and a connector/gateway that rejects every non-text event are required. Those platform controls belong to Codex #2's infrastructure work and need separate verification.

No Codex process, provider request, OAuth flow, credential store, token, or account status was accessed for this assessment. The protocol frames and event identities below are synthetic fixtures. They test Omnis's contract logic only; they are not app-server conformance or host-security evidence.

## Repository gap analysis

Reusable main contracts:

- `RuntimeAdapter` is deliberately `kind: 'mock'`; `apps/worker/src/server.ts` constructs `SandboxedMockRuntimeAdapter` directly. Do not register a Codex provider or add a production selector.
- Task/run queue admission, owner `mock.execute` authorization, leases/generations, stop handling, PostgreSQL event sequences, SSE replay, and recovery already exist for the mock lifecycle.
- `packages/contracts/src/connector-authorization-schema.ts` and `connector-broker.ts` define a **synthetic-only** owner approval, immutable project/task/profile revisions, prompt digest, empty capability tuple, bounded limits, one-use IDs, synthetic provenance, and `unknown` usage/outcome shapes. Their literal `providerId: synthetic`, model/connector IDs, and synthetic row constraints do not authorize OpenAI or another live provider.
- `apps/worker/src/synthetic-broker-run-coordinator.ts` and its tests exercise durable synthetic admission, correlation, recovery and unknown outcomes. They remain a test-only broker path and are not the production run execution path.
- `apps/worker/src/test-support/fake-codex-app-server.ts` now models a small documented app-server wire subset in-process. It has no process, socket, network, OAuth, or credential interface. Production continues to use mock only.
- `packages/runtime-protocol` Stage A is a pure synthetic policy/replay protocol. Its request hash rejects invalid protocol-version types. It has no transport, durable replay store, production key resolver, external side effect, or connection to worker admission.

Current boundaries that must remain unchanged:

- Run and run-event contracts constrain execution to `runtimeKind: "mock"`, `synthetic: true`, `source: "mock"`, and unknown usage. Do not label fixture output or existing mock activity as provider evidence.
- There is no provider-specific live authorization, consent endpoint, credential broker, provider provenance schema, app-server process, or live connector egress policy.
- Persisted mock events and SSE history are durable and ordered. The new in-memory fixture projection does not change DB event persistence, recovery, owner result acceptance, or APIs.

- [RFC 8785 JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785)

The published app-server reference documents JSON-RPC-shaped messages with the `jsonrpc` header omitted on the wire. Default local transport is stdio with newline-delimited JSON. WebSocket transport is described as experimental/unsupported; Unix-socket transport uses a WebSocket upgrade. Protocol schemas generated by `codex app-server generate-ts` or `generate-json-schema` are specific to the Codex binary version. This repository does not pin an app-server binary or generated schema; exact-version compatibility is unverified.

### Text-only request feasibility

The protocol can carry a text input item and stream agent-message text. That establishes a feasible text transport shape only. The docs expose built-in and configurable tool paths and do not establish a complete `tools: []` or equivalent trusted deny-all mode for every shell, file, MCP, browser, network, delegation, or privileged action. A prompt instruction, read-only sandbox setting, approval setting, no-tool fixture, or absence of tool declarations is insufficient evidence.

Until an exact version and effective app-server configuration are separately assessed, the enforceable design must assume app-server can request tools. The future platform must prevent the corresponding process/file/network effects independently and the connector must fail closed on any tool/control event. A negative test at this fixture parser proves only that the parser rejects its synthetic message.

## Authentication, consent, and credential custody

Official SIWC documentation describes an app-owned OAuth registration and user-consent flow for supported open-source/locally hosted apps. It uses an app/client identity and granted scopes; a valid identity token alone does not establish that ChatGPT plan usage was granted. The docs state the host app owns token renewal for the external-token app-server configuration and supplies the access token to its app-server child process (documented as an environment variable). The preview imposes request requirements including streaming and `store: false`, omits some request fields, and documents limitations for paid or remotely hosted apps.

These are separate decisions and identities:

1. A pre-existing local Codex CLI login is for that CLI/client. It is not Omnis registration, Omnis owner consent, or permission to reuse its credential.
2. A future Omnis SIWC registration and provider-side owner consent would be a distinct provider connection. This assignment did not register an app, open OAuth, or use a token.
3. Omnis owner approval for a particular task/run is separate from provider connection consent. It must bind the exact immutable operation and be revocable independently.
4. The credential broker/secret store must own token acquisition, refresh, rotation, and revocation. Tokens must not enter PostgreSQL run records, event payloads, worker environments, prompts, task workspaces, logs, or artifacts. Because the documented app-server setup passes the access token to its child process, that process must have a dedicated identity and a reviewed secret-injection boundary.
5. Provider account plan, model entitlement, and product-policy/terms approval remain owner/provider decisions. Model catalog or account-level usage responses are not entitlement for an exact operation and do not prove per-run cost.

## Offline contract implemented by this change

`apps/worker/src/test-support/codex-app-server-contract.ts` is an in-process, test-only parser/projection and operation-state reducer. `apps/worker/src/test-support/fake-codex-app-server.ts` injects synthetic app-server-shaped messages into the existing mock adapter boundary. Neither module is imported by production startup.

The fixture contract provides:

- A bounded single-text `turn/start` request builder with no tool fields. It is a fixture constructor, never a transport request.
- Strict parsing of a small notification subset: turn started, text item start/completion (including documented optional `phase` values), text delta, and terminal completed/failed/interrupted. Server-initiated method calls, tool/non-text items, malformed frames, unknown methods, and identity mismatches are denied.
- Local correlation to `runId`, operation UUID, execution generation, synthetic session ID, thread ID, and turn ID. Identity is validated before projection.
- Monotonic fixture delivery sequence and delivery-ID deduplication. Reusing a delivery ID with changed bytes or a changed sequence, and any new out-of-order or gapped sequence, are rejected. After disconnect the projector stays unknown and rejects stream events; only a separate authoritative reconciliation can resolve it. Delivery IDs and sequence numbers are **synthetic harness metadata**, not app-server-provided replay guarantees.
- UTF-8 frame/delta/aggregate output caps. Output is emitted only for the accepted text item; the completed item must match the accumulated deltas.
- Completion-after-cancel-request remains completed when app-server reports completion. Cancellation before dispatch uses a distinct local state; after possible dispatch it is confirmed only by matching interrupted terminal status. Disconnect, lost submission acknowledgement, or lost cancellation outcome becomes unknown.
- Synthetic usage normalization that checks nonnegative safe integers and total consistency. Missing usage is `unknown`; this shape is not claimed to match the undocumented app-server usage notification payload.
- Safe failure categories. Raw provider failure text is not included in normalized events.
- An in-memory operation reducer with separate pre-submission and possible-dispatch cancellation states, explicit provider-terminal evidence signals, and one-way `submission_attempted`/`unknown` transitions. Bare cancellation confirmation is allowed only before submission is attempted. Unknown can reconcile to a terminal observation but cannot return to a submission state. The caller must establish authoritative evidence before using a `reconciled_*` signal; this pure reducer cannot verify evidence provenance. It demonstrates transition rules only; it is not durable authorization, a provider operation, or a production retry guard.

## Backend contract for a separately approved future implementation

No live HTTP/API request, response, endpoint, task/run state, or database schema changes are introduced here. The following contract is **PROPOSED / NOT ACTIVE**.

### Existing lifecycle compatibility

Current task states are `open`, `in_progress`, `in_review`, and `completed`. Current run states are `queued`, `running`, `stopping`, `completed`, `cancelled`, `failed`, `interrupted`, and `unknown`. A future provider run should reuse these states: queued/submitting work enters `running` only after the durable worker claim; a stop request enters `stopping`; verified provider terminal state maps to completed/failed/cancelled/interrupted; ambiguous external submission or cancellation remains `unknown`. Do not add a task state or treat provider text as task completion.

Today, result acceptance remains owner-only and applies only to the latest eligible completed mock Run with persisted output and no active lease. A completed Run is not an accepted Task. A real provider Run must not become eligible under this mock-only API/DB contract; provider provenance, result storage, acceptance eligibility, API serialization, and event ACLs need a separately reviewed backend change.

Existing API responses, owner authorization, task acceptance endpoint/error codes, and SSE contract do not change in this PR. No new provider API route or error code is introduced.

### Immutable owner-approved operation

A future operation grant must bind owner identity and explicit decision to:

- Project ID and revision; task ID and revision; exact latest run ID, execution generation, and one-use operation ID.
- Immutable agent profile ID/version and digest; exact prompt digest and prompt-rendering version.
- Provider ID, provider account reference, app-server binary/version and protocol schema version, runtime identity, model ID, and policy/entitlement scope.
- Exact allowed tool set, empty for the first operation; output bytes/tokens, duration, concurrent-run limit, and applicable usage ceiling.
- Issue/expiry time, revocation generation, one-use JTI/idempotency key, and audit correlation identity.

The grant must be checked fail-closed immediately before provider dispatch. Provider connection consent and task-level owner approval are separate. Revocation must prevent a not-yet-dispatched operation and signal the active connector; whether already-dispatched provider work can be stopped is not assumed. Replays must return/read the same operation outcome, never mint a new provider submission.

The existing connector authorization schema is locked to a synthetic provider and cannot be reused as live authority without a separately reviewed schema/policy implementation. Do not relax its literals or the `mock` DB/runtime gates here.

### Request, response, and identity

Future internal request shape (illustrative only):

```ts
type ProviderRunRequest = {
  operationId: string; // one-use UUID
  runId: string; // canonical Omnis run ID
  generation: number; // current durable lease generation
  taskId: string;
  projectId: string;
  profileVersion: number;
  promptDigest: `sha256:${string}`;
  providerId: string;
  accountRef: string; // opaque non-secret connection reference
  runtimeVersion: string;
  modelId: string;
  allowedTools: [];
  limits: { maxOutputBytes: number; maxDurationMs: number; maxConcurrentRuns: 1 };
};

type ProviderRunAccepted = {
  operationId: string;
  runId: string;
  generation: number;
  state: 'submission_attempted' | 'submitted' | 'unknown';
  providerThreadId?: string;
  providerTurnId?: string;
};
```

The API must not expose provider tokens. The response acknowledges only the local operation state that is known. A lost response after submission does not become a failed/no-op result.

The current DB Run ID is not interchangeable with Stage A's UUID `run_id`: current main mock IDs include values like `run-0001`, while Stage A runtime protocol schemas require UUIDs. The existing synthetic broker uses separate correlation/attempt UUIDs in its synthetic contract. A future integration must define and persist an explicit local-run-to-external-operation mapping; this assignment makes no ID-format migration.

### Event projection and durable persistence

The app-server stream does not document a universal stable event ID or reconnect replay cursor. A future connector must persist the operation ID, exact local run/generation, thread/turn IDs when received, item IDs, connection epoch, and a local monotonic event sequence. Provider events must be validated and transactionally persisted before SSE publication. Deduplication must use a documented stable identifier where one exists; local fixture delivery IDs cannot be promoted to provider guarantees. If a disconnect leaves a gap that cannot be reconstructed safely from authoritative thread history, mark the run unknown and retain the original submission.

Proposed local lifecycle vocabulary:

`requested → authorized → submission_attempted → submitted → started → text_delta* → completed | failed | interrupted | unknown`

Cancellation is `cancel_requested` followed by matching terminal `cancelled`/`interrupted`, `completed`, `failed`, or `unknown`. A cancellation acknowledgement alone is not terminal. A completion may race with cancellation and must win if it is the verified provider terminal result.

Current `RunEventSchema` only accepts `source: "mock"` and `synthetic: true`, and the current Run/DB usage schemas do not represent provider provenance. Real-provider persistence therefore requires a separate migration, ACL and event-contract review. No provider events may be passed through the existing mock event schema as if they were real.

### Submission uncertainty and recovery

Persist a unique operation identity and a durable `submission_attempted` fence before handing the request to the provider boundary. Once bytes might have been dispatched, timeout, connection loss, process death, or missing acknowledgement means `unknown`; it does not mean the request failed. Never automatically issue `turn/start` again for an unknown operation. Recovery may read/reconcile the same known thread/turn and resolve only with authoritative terminal evidence. If no provider identity was received before a lost acknowledgement, no safe retry is inferred. A new attempt requires a separate explicit owner-approved operation after the old operation is resolved or policy handles the unresolved exposure.

For cancellation, send `turn/interrupt` only for the stored thread/turn pair. Confirm cancellation only from the matching `turn/completed` interrupted state. If that response or terminal event is lost, retain unknown and use an independently approved exact-workload termination/reconciliation path; do not claim upstream cancellation based on killing the local process.

## Stage A review findings disposition

The following notes respond to the exact-revision concerns recorded on [PR #110](https://github.com/Jeysibn/omnis-os/pull/110):

- **`SAVED_RESULT` classification:** `packages/runtime-protocol` now has a dedicated `ReplayClassificationSchema` containing `SAVED_RESULT`. It intentionally does not extend policy/audit `ClassificationSchema`; this prevents a reducer-only value from being accepted as a policy decision/response. The replay reducer remains pure and in-memory.
- **Replay reducer vs policy evaluation:** `reduceReplay` is not called by `evaluatePolicy`, does not persist or consume anything, and does not grant dispatch authority. It is reducer algebra only. A later production authorizer/gateway must implement a single durable consume-before-dispatch transaction/journal and concurrency/crash tests.
- **Canonicalization:** Stage A's `canonicalJson` is a local deterministic serializer, not a claimed general RFC 8785 implementation. Current framed input and claim schemas constrain the signed domain; current tests cover fixed local canonical bytes only. Cross-language JCS compatibility remains unproven. Before signing across services/languages, pin the canonicalization profile, use compatible official vectors (including Unicode/numeric cases), and test golden message bytes and digest across implementations.
- **Key ID:** `verifySyntheticCapability` now passes the protected `kid` to its verifier callback, with a regression test. This is still synthetic callback plumbing; it does not load a key, enforce a trust store, rotate/revoke keys, or authorize production.
- **Run ID formats:** Stage A's UUID runtime `run_id` and canonical DB Run IDs remain different domains. The future mapping described above is required; no current identifier or database constraints were changed.
- **Clock/expiry:** Stage A accepts an injected integer time for deterministic tests. It does not establish a trusted production clock, monotonic expiry, bounded skew, issuer clock, or revocation freshness. A future short-lived capability must define those semantics and test clock changes, expiry boundaries, stale generation, and revocation under restart.

## Handoff to Codex #2 — infrastructure prerequisites

No Codex #2-owned infrastructure is implemented here. Before any connection is considered, Codex #2 must establish and independently test:

- Separate service identities and rootless Core/Runtime Engine boundaries; provider connector has no raw Engine socket, launcher, DB, authorizer, task workspace, developer-home, or inherited-descriptor access.
- Authenticated local IPC with kernel peer identity, strict length/framing bounds, pinned protocol version, and the gateway as the only Runtime Engine socket holder. The provisioning/update path must not be controlled by the launcher it constrains.
- Host-enforced no-tool boundary: no shell/process spawn, workspace or host filesystem access, MCP/browser, arbitrary network, forwarding, or delegation side effect even if app-server emits the corresponding request. A parser denial by itself is insufficient.
- Credential custody in a dedicated broker/secret store, no token in worker/sandbox/API/logs/events, least-privilege app-server identity, and tested refresh/revocation/restart handling. The documented child-process token environment is a sensitive boundary.
- Explicit, default-deny provider egress scoped to approved provider destinations with IPv4/IPv6/DNS and proxy bypass tests; no token tunnel.
- Enforced per-run/aggregate CPU, memory, process, file, output, duration and concurrency limits; independent termination and startup fencing after worker/gateway/daemon/host restart.
- Exact-operation audit and provenance, bounded redacted event storage, and unknown-outcome recovery with no automatic provider resubmission.

These requirements align with PR #110's documented unimplemented controls. Its owner decisions, ADR-0012 ingress blocker, independent terminator, gateway packaging/provisioning, and real disposable test work remain separate gates.

## Handoff to Claude — future UI contract (NOT YET ACTIVE)

PR #108 owns the current frontend workflow and is not modified by this change. A later UI change may use the following proposed display contract after backend/provider gates are approved:

- Show provider, account alias, runtime/app-server version, model, profile version, prompt/operation digest confirmation, empty tool set, configured limits, usage caveat, and provenance before owner approval. Never expose tokens.
- Proposed approval request returns an immutable `operationId`, `runId`, generation, exact binding summary, expiry, and approval state. Explicit deny/revoke must be available. Approval is single-operation and is distinct from connecting an account.
- Render lifecycle states truthfully: requested, awaiting approval, authorized, submitting, submitted, running, cancellation requested, completed, failed, cancelled/interrupted, and **outcome unknown**. Do not show `unknown` as failure or completion.
- Stream only persisted, run-correlated text deltas with a durable cursor. Label provider origin and preserve gaps/reconnect state. Show final completion only after authoritative terminal reconciliation and owner result acceptance remains separate.
- Cancellation UI must say requested until confirmed. If acknowledgment/terminal evidence is missing, show unknown and allow refresh/reconciliation; never auto-submit again.
- Display usage only as provider-reported/verified per-turn measurement with source and timestamp. Otherwise display unavailable/unknown; do not convert account-level activity into run tokens or cost.

This handoff is a proposal, not a request for Claude to change PR #108.
