## Contract alignment

This design reads the merged backend contract `omnis.ao107.local-runtime-handoff.v1` from PR #147 and the versioned Issue #149 response `omnis.ao107.b2-resource-identity.v1`. The former binds owner consent, SIWC connection, host principal/generation, authenticated process role/instance, and exact provider operation. The latter extends the same attempt with the exact Docker resource and platform action. They are complementary; neither grants platform acceptance or authorizes an operation.

The admission seam requires these grant fields and compares the resource binding and reservation against them: owner decision and attempt IDs; host, daemon, and process registrations and generations; immutable resource kind/object ID; canonicalization version and configuration fingerprint; parent bindings; creation provenance tied to authorization/run/attempt; lease ID/generation/expiry; exact action; policy revision; authorization revocation generation; and the one-use dispatch-fence reservation. Names and labels do not participate. A caller selection reference may select a candidate but must be resolved by authenticated platform inventory before any action.

The merged contract does not define a trustworthy Docker resource discovery API, and Issue #149 says no backend identity fields should be wired as authoritative until a trusted platform identity/registration interface exists. The new module is therefore an unconnected fail-closed seam. Its injected authority callbacks must be implemented and separately reviewed before any production use; fixtures only model their expected behavior.

## Trust anchor and continuity scenarios

No accepted trust anchor for this WSL2 installation is established in the repository or by this work. A local file, database row, filesystem UUID, WSL distribution name, `machine-id`, Docker daemon ID, PID/UID/container ID, label, `ext_agent_host_id`, or signed envelope cannot independently prove anti-clone or anti-rollback continuity. Rootful Docker can assert or alter daemon-reported object state. Immutable Engine object IDs and configuration fingerprints can detect drift only when checked against a trusted daemon/host registration.

WSL supports distribution export/import, including moving and restoring a distribution. Therefore identity keys, counters, and ledgers stored only in that distribution can be copied or rolled back with it; they cannot serve as the independent monotonic anchor. See Microsoft’s [WSL FAQ](https://learn.microsoft.com/en-us/windows/wsl/faq) and [basic WSL commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands).

A candidate trust architecture needs an owner-controlled external monotonic registrar whose key and state are outside the restorable WSL distribution; fresh authenticated challenges; non-reused host/daemon/process/resource generations; durable revocation and dispatch-fence generations; single-use action reservations; and explicit re-enrollment after continuity breaks. A Windows hardware key alone is not accepted as sufficient: clone access to a signing oracle and registrar rollback/recovery behavior must also be addressed. No current host change or hardware assumption is proposed as fact.

## Source-only admission seam

`scripts/platform/b2-continuity-admission.mjs` validates the exact grant/resource binding, requires injected authenticated-evidence and reservation verifiers, checks the reservation’s exact attempt/resource/action and all relevant registrations/generations, then invokes one injected action. Missing authorities, mismatch, stale/revoked evidence, or malformed reservation denies before action. An exception after action may have started returns UNKNOWN for the same attempt; the seam never retries.

The seam cannot itself authenticate callbacks, check expiry against trusted time, establish freshness, serialize reservation with revocation, persist one-use state, perform a resource lookup, or prove action termination. Those guarantees belong to the yet-unbuilt platform registrar/action gate described by the Issue #149 addendum. The synthetic positive test proves only the policy path with a fake authority. Adversarial tests cover absent authority, object/parent/provenance substitution, rejected rollback/staleness/expiry/revocation, altered reservation identity/generation/fence, unauthenticated reservation, and ambiguous dispatch. No Docker API, resource enumeration, host configuration, subprocess, network access, or target test is part of this implementation.
