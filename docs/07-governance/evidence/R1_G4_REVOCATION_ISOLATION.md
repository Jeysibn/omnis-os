## Locking and failure semantics

The admission path still serializes the global active-run cap and idempotency check with advisory key `70463909136524`. `PostgresRunStore.admitRun` now sets transaction-local `lock_timeout = '3s'` before acquiring it. The same bound applies to later row-lock waits in admission. PostgreSQL lock timeout is translated to a retryable `admission_busy` error with HTTP 503. The transaction rolls back, so no run, queue job, idempotency record, or grant consumption is committed on this response. Normal concurrent idempotent admissions retain their existing serialized behavior.

Revocation retains its migration-0008 three-second lock timeout and existing row-lock ordering. Unconsumed revocation locks grant then writes the audit row; consumed revocation locks run then grant, matching worker lifecycle transitions. Runtime can acquire these rows through legitimate runtime functions or lifecycle operations and retain locks in an open transaction. When that happens, each revoke attempt fails with SQLSTATE `55P03`; the API says `authorization_busy`, the grant remains active, and a later retry can succeed after contention clears. A 503 is a failed revoke, never a successful or effective revocation.

The effective revocation boundary remains the successful commit of the authorizer transaction. A claim or lifecycle operation serialized before that commit may complete first. Heartbeat locks the run and then the active grant before renewing; if it waited behind revocation, it checks the post-commit grant state and does not renew. Other operations reaching their durable authorization check after the commit fail closed. No external effects exist in the mock runtime; this boundary does not promise cancellation or reversal of an already completed external effect in a future system.

These are bounded-failure mitigations, not runtime-independent availability. A compromised or stalled worker process that retains runtime credentials can repeatedly hold the relevant rows or the global admission key. G4-3 process and credential separation remains a prerequisite to stronger isolation.

## Legacy provenance

Migration 0008 uses the recorded `0005_durable_authorization` application time to classify historical active grantless runs. Runtime has no INSERT or UPDATE privilege on `runs.created_at`; the disposable PostgreSQL test verifies both catalog privileges and actual rejected SQL attempts. A database staged through 0007 demonstrates that a newer grantless run created before applying 0008 is not marked as historical. Its execution attempt remains fail-closed. Only the run created before 0005 receives migration provenance and can enter the existing safe terminal recovery path.

The backup/restore integration now includes a synthetic provenance marker in the source archive, confirms it survives restore, and confirms the restored runtime role cannot read `legacy_unscoped_runs`. The marker does not authorize execution.

## Remaining risks and gates

- **Availability:** G4-12 and G4-13 remain partial. Runtime can repeatedly cause explicit 503 failures and prevent successful revoke/admission until contention ends. Timeouts bound individual attempts; they do not guarantee control-plane progress.
- **Trust boundary:** `omnis_authorizer` and runtime credentials still reside in one worker process (G4-3). This milestone does not isolate a compromised process.
- **Authorization:** The system remains limited to task-scoped, single-use `mock.execute` authorization. No provider integration, credentials, connector egress, or arbitrary tools were added.
- **Audit:** Authorization and lifecycle audit remain transactional and access-restricted but are not cryptographically immutable or externally anchored.
- **Future provider gate:** Independent authorizer process/credential boundary, trusted credential broker, provider policy review, per-run connector authorization, egress controls, and in-run revocation for external effects remain unapproved prerequisites. ADR-0010 remains Proposed.
