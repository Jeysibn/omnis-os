## Deployment and privilege boundaries

The CI-only `scripts/host-security/verify-disposable-systemd-deployment.sh` requires `CI=true`, an explicit opt-in variable, root, a running systemd PID 1, and an active Docker service. It refuses pre-existing Omnis users, groups, service paths, units, and occupied ports. On the ephemeral Ubuntu 24.04 GitHub runner, run `41677410902` passed: it provisioned identities, installed a root-owned application copy and synthetic secrets, applied the actual systemd units, ran worker-boundary checks, and created/approved/completed a synthetic task through API → authorizer → worker → restricted launcher → mock container. The installed-service probe removed the service resources during cleanup. The development host was not touched.

The shared development machine was not changed: no privileged host script was executed, no identities/groups/units were installed, and no shared Docker service was restarted. Local `pnpm dev` runs under one developer identity and is not isolation evidence. The runner test demonstrates the proposed systemd deployment on a disposable Ubuntu 24.04 host; it is not verification of a production or homelab installation. The launcher retains rootful Docker group membership, which is root-equivalent; the launcher, kernel, Docker daemon, host supervisor, and trusted API remain in the trusted computing base.

## Owner-decision scope and deferred gates

For the single-owner synthetic mock gate, owner authentication and CSRF remain at the API; the API and authorizer run as different OS users and communicate through a private OS-owned UDS plus a separate static API-authorizer token. The authorizer records fixed `owner` attribution transactionally after the trusted API request. Existing request IDs remain idempotency keys, and lost responses remain `authorization_outcome_unknown` with safe same-key retry/readback.

Per-decision signed owner assertions, HMAC binding of method/path/body/timestamp/request ID, a replay ledger beyond existing database idempotency, and a coordinated token-rotation drill are **not implemented**. The current ADR-0011 proposal scopes the static API token plus OS-owned socket to the single-owner synthetic mock deployment; these stronger controls are explicit prerequisites before real-provider authorization or multi-user/step-up decisions. The token and fixed actor do not protect against compromise of the API, launcher, host, or kernel. ADR-0011 remains Proposed. ADR-0010 remains Proposed and its backup cryptography requirements are unchanged.

## Disposition

N-1, P-5, and N-2 have implementation and regression coverage, including a passing installed-systemd deployment test on a disposable GitHub-hosted Ubuntu 24.04 runner. CI-simulated identities and deployed systemd checks are both recorded separately. G4-3 remains **Partially Fixed** overall: the tested worker cannot read authorizer secrets, access its socket, write trusted code, or reach Docker directly, but the rootful launcher remains root-equivalent and the single-owner static-token model lacks signed per-decision assertions, extended replay protection, and a rotation drill. These controls remain gates before real-provider or multi-user authorization; no real provider authorization or execution is approved.
