## Risks and blockers

1. **Hermes tool scope:** bearer auth protects the API but does not by itself constrain the powerful toolset. Do not call the API with a read-only prompt until a verified tool allowlist and isolated workspace are in force.
2. **Provider-account usage:** existing local sign-in state is personal account material. Do not pass it into a web/API process or a shared service. Any future background run requires the supported provider authorization flow and explicit user consent.
3. **Claude automation policy:** subscription authentication exists on the machine, but this does not approve reuse by an app-owned unattended worker. Keep disabled until reviewed.
4. **Host infrastructure:** The original command shell lacked the current Docker supplementary group. A fresh WSL login showed the already-configured `docker` group and successfully ran Compose; no socket permissions or group membership were changed. Docker group membership is root-equivalent and must remain a deliberate host-owner decision.
5. **Repository baseline:** workspace was empty and had no `.git`, source documentation pack, or existing implementation to preserve. The initial documentation commit records the handoff before code is added.
6. **Dependency reproducibility:** the initial Phase 0 install could not reach the registry. During R1-G1, the registry responded, pnpm 12.16.1 installed dependencies, `pnpm-lock.yaml` was generated, and CI now uses frozen-lockfile installs. Clean-worktree verification is recorded separately below.

## R1-G4 authorization availability and legacy recovery — PR #7

PR #7 adds forward-only migration `0008_revocation_availability_and_legacy_run_recovery.sql`. It removes the shared advisory lock from direct grant consumption and revocation because PostgreSQL makes advisory lock functions executable by `PUBLIC`; a restricted runtime session could hold the known key and block owner revocation. A real PostgreSQL 17.6 test reproduced the pre-fix wait (`pg_locks` showed the revoker waiting on the advisory lock). After migration 0008, the same runtime session lock no longer blocks revocation. Admission and revocation serialize per grant with a fixed row-lock order; row-lock contention in revocation fails after a transaction-local 3-second `lock_timeout` with SQLSTATE `55P03`, rolls back state and audit, and is mapped to HTTP 503. The existing global admission-cap advisory lock still uses that key, so a runtime session can still block new admissions; this is an explicitly open reliability risk. The timeout is bounded failure, not a guarantee against repeated database contention or all runtime-originated denial of service.

Migration 0008 records provenance for active grant-less rows created before migration 0005 applied. These rows can be denied at claim or moved to cancelled, failed, or interrupted states, with audit entries attributed to `service:omnis-runtime` and no synthetic grant. They cannot start or complete. Newly created grant-less rows are not marked and continue to fail closed. Full local checks, actual Docker sandbox tests, PostgreSQL authorization tests, the legacy upgrade from `708d0f5e9b6083da852e26c0643c60c0f5879f85`, recovery, backup/restore, and build passed on the local feature branch; exact branch CI and review status are recorded in [PR #7 evidence](evidence/R1_G4_AUTHORIZATION_AVAILABILITY.md). Real providers remain disabled and G4-3 process separation remains open.

## R1-G4 revocation isolation and admission availability — PR #8

PR #8 adds a transaction-local three-second `lock_timeout` to run admission, mapping PostgreSQL lock timeout `55P03` to a truthful retryable HTTP 503 `admission_busy`. The global advisory key remains, so a runtime session can continue to deny admissions while holding it; timeout bounds one attempt but does not guarantee progress. Revocation likewise remains bounded, not independent of runtime-held grant/run locks: each `503 authorization_busy` means the grant is still active, and repeated lock retention can continue to prevent a successful revoke. Both findings remain **Partially fixed** pending stronger process/credential isolation.

Lease renewal now follows the consumed-revocation lock order (run row, then active authorization row) inside one transaction. A trigger-gated PostgreSQL test verifies that a heartbeat waiting behind a committing revocation does not renew after the grant is revoked. The legacy-upgrade drill now stages a database through migrations 0001–0007, verifies that only the pre-0005 run receives legacy provenance, rejects runtime attempts to set or alter `runs.created_at`, and keeps newer grantless runs fail-closed. Backup/restore verifies that trusted provenance records survive without runtime read access. Local full checks, Docker sandbox tests, PostgreSQL upgrade/recovery, and backup/restore evidence are recorded in [PR #8 evidence](evidence/R1_G4_REVOCATION_ISOLATION.md). No provider integration or arbitrary tool execution is enabled.

## R1-G4 PostgreSQL timeout and role-setting hardening — PR #9

PR #9's role provisioning configures new `omnis_runtime` sessions with `lock_timeout=3s`, `statement_timeout=20s`, and `idle_in_transaction_session_timeout=20s`; `omnis_authorizer` receives `3s`, `15s`, and `20s`. The migrator's role defaults for these parameters are reset to preserve migration headroom. `idle_session_timeout` remains unset to avoid unexpected pooled-connection termination. These are operational defaults only: PostgreSQL sessions can override them, existing pools retain their session settings until reconnect, and an idle session-level advisory lock is unaffected by `idle_in_transaction_session_timeout`.

Role provisioning is idempotent and refuses relevant database-specific timeout overrides. Restore role-integrity validation checks actual `pg_db_role_setting` role defaults and database-specific settings; disposable tests verify new runtime/authorizer connection settings, a runtime `SET` override, a hostile database override, and pool recovery after PostgreSQL terminates an idle transaction. Worker heartbeat now adds a transaction-local three-second lock timeout before the existing run→grant lock order. SQLSTATE `55P03` rolls back and is returned as a failed renewal, causing safe sandbox interruption/reconciliation without replay. The real API contention integration asserts bounded 503 responses, unchanged authorization/audit on failed revoke, and no partial run/idempotency state on failed admission. See [PR #9 timeout policy evidence](evidence/R1_G4_POSTGRES_TIMEOUT_POLICY.md).

G4-17 is fixed for the heartbeat renewal transaction; G4-18 is covered at the worker API boundary. **G4-16 remains partially fixed/open**: a runtime credential holder can alter its own session defaults and can continue to cause bounded admission/revocation failures while retaining locks. G4-3 authorizer/runtime process and credential separation remains a prerequisite for a trusted control-plane boundary. N-8 lifecycle-column enforcement and all real-provider policy, connector, credential-broker, and egress controls remain separate gates. This PR does not enable real model inference or arbitrary tools.
