# Stage A Offline Security Harness

This directory contains test-only, deterministic fixtures for the proposed P0-R2.1 runtime contract. It does not implement a Gateway, Authorizer, Docker client, terminator, durable journal, or provider connector. Its fixtures use in-memory state and synthetic identities, IDs, payloads, signatures, and responses.

**Source baseline:** `0e1efbe803826059089fcfc16de65e9bb081bfcf` (current `main`, including PRs #112 and #115 at harness expansion start). Runtime-protocol code is consumed unchanged. Contract reference: PR #110 head `834749036a70845d95debd8ccdf7dd5085d8b675`; its remaining specifications are provisional and do not resolve M-3/M-4 or authorize later stages.

Run with:

```bash
node --experimental-strip-types --test tests/offline-security-harness/*.test.mjs
```

The harness imports pure functions from `packages/runtime-protocol`. It does not import `node:net`, HTTP/TLS clients, Docker libraries, `node:child_process`, `node:fs`, or environment/credential loaders. The fake Engine recorder only validates and stores a JavaScript request object. The synthetic capability verifier accepts one fixed test key ID and an all-zero fixture signature; it is not cryptographic verification and must not be reused by application code.

`advanced-fixtures.test.mjs` adds nine grouped suites. They exercise C-1 outcome authentication/report replay/crash recovery; C-2 registration-before-start, armed stop leases, deadline behavior and termination evidence; R-03 separation of execution and stop authority; and C-3 pre-fence/DB/anchor ordering, revocation/lease rollback, stale revisions, duplicate/conflicting receipts and fail-closed admission. The suites use named deterministic IDs, fixed synthetic key material and in-memory Maps only. Test names and assertions are the per-case inventory; grouped suites include their positive, negative, crash and outage variants. Codex #1's exact-head reviews identified fixture-model findings F-01 through F-06; this revision adds regression cases for revocation/consume ordering, dispatch-before-completion, anchor-retained identity sets, registration revision order, stop-ID binding, and non-replaceable lease replays. These remain mock-only contract tests, not independent approval or enforcement evidence.

The C-3 fixture represents a possible two-step pre-fence then database commit then anchor-finalize contract solely for testability. It does not select the owner's M-3 solution. In particular, an in-guest journal cannot detect a snapshot that restores both the journal and ledger; only an owner-approved independent anchor with experimentally established custody could address that threat. M-4's real terminator and registration authority are also not implemented.

This harness does **not** prove:

- Host-level isolation, Docker/rootless Engine confinement, effective container limits, or actual request acceptance by a daemon.
- Real cryptographic key custody, signatures, live peer credentials, or identity mapping.
- Durable PostgreSQL atomicity, database grants, fsync/power-loss guarantees, or rollback-resistant storage.
- Kernel-enforced cgroup registration, independent termination, or actual process/shim/helper termination.
- Independent IPv4/IPv6, DNS, loopback, AF_UNIX/AF_VSOCK, RootlessKit, proxy, or other egress enforcement.
- VM/WSL2 compatibility, Windows-local ingress provenance, or real provider execution safety.

There is no socket, process, filesystem, network, Docker client, daemon, service-manager or provider operation in these tests. They use no credentials or external destinations.

## Stage B prerequisites

Stage B is outside this PR and remains blocked pending separate explicit owner authorization. The limited Stage B subset may test real rootless Engine setup and direct kernel/socket controls without the integrated Gateway or terminator; it must not imply those controls are ready.

Before any Stage B VM is created or modified, its request must name and approve:

- A disposable Linux VM provider/hypervisor, exact OS image and kernel, rootless Docker version/configuration, and immutable source/fixture hashes.
- Guest-root operations, dedicated users and subordinate ID ranges, systemd/cgroup-v2 changes, data roots, disk/resource limits, network attachment, and any host permissions.
- Allowed Stage B test IDs only; synthetic data/credentials; no provider access; no owner data; and no access to the active WSL2 or Docker installation.
- Independent cleanup/destruction authority, exact resource IDs, evidence paths/retention, stop conditions, and post-test evidence that the VM and its workloads are gone.
- Required Codex #1 and Claude review status and explicit owner authorization for that exact VM and privilege envelope.

Stage B evidence must inspect the real daemon's effective configuration, service identity/socket and UID maps, separate storage, cgroup-v2 controllers and limits, and applicable direct local-IPC/network enforcement points. An unreachable destination is not proof of a deny rule. Per-run termination, rollback-anchor behavior, Gateway enforcement, integrated egress and recovery remain Stage C requirements; M-3 and M-4 remain unresolved design/owner gates. WSL2 remains Stage D and requires applicable Linux VM evidence plus separate authorization.
